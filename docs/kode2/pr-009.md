## 对拍 golden 双向门禁(fixture 驱动,ARCH-012 不做性能对比)

- 正本:`crates/kode-scheduler/tests/golden/scheduler-parity.json`
  (Rust `dump-scheduler-golden` 生成,**10 场景**)。
- 场景面 = 调度决策面:enqueue 合并/过期丢弃/过期取消决策、优先级执行序、
  交互冷却推迟与恢复、keyed 复用/失败恢复、批量取消、同优公平序、混合风暴。
- Rust 侧:`tests/scheduler_golden.rs` 重生成比对 + 结构完整性;
- TS 侧:`tests/kodeSchedulerParity.test.ts` 用真实 `IndexScheduler` +
  `vi.mock('perf_hooks')` 注入逻辑时钟 + fake timers 复算同一串 ops,
  **11/11 通过;逐场景比对字段 = decisions + runOrder + 4 计数 +
  queuedByPriority + keyedTasks + 5 个共享指标,合计 148 字段全对齐 = 100%**。
- 时钟口径:TS 冷却时钟来自 `perf_hooks.performance`,fake timers 覆盖不到,
  故测试内注入可推进逻辑时钟(`__kodeParityClockMs`),与 Rust
  `advance_clock` 同构;`drain` 的时钟前跳语义与 Rust `drain` 逐步对齐。

## 风暴合并实测样例(单元门禁 `tests/scheduler_units.rs::storm_buffer_*`)

- 100 个变更事件集中 3 个文件 → `flush()` 出 **3 条任务**(每文件最新版本:
  /f0→v100、/f1→v98、/f2→v99),`merged=97`;事件零丢失(`events_seen=100`);
- 缓冲超限强制落批:容量 2 收 5 事件 → `forced_flushes=2`、余 1,不丢事件。

## 取消实测样例

- 句柄级:queued 任务 `cancel(id)` → `Cancelled`,运行中/已终态任务取消返回
  false 且不改变状态(`cancel_running_task_is_not_interruptible`);
- 批量:3 个 queued 后台任务 `cancel_queued_tasks("test-reset")` → 返回 3、
  `cancelled=3`、drain 后 `completed=0`(对拍场景 cancel-queued-batch:
  decisions=`["queued","queued","queued","cancelled:3"]`);
- 版本让位:同文件 v1 在队、v2 入队 → v1 取消(计 stale),仅 v2 执行
  (对拍场景 newer-version-cancels-older)。

## 崩溃恢复实测样例(`tests/journal_units.rs`)

- 3 个 queued 任务写台账 →「崩溃」→ 新调度器 `load_journal` + `recover`
  (其中 /stale.def 已被编辑到 v9,v2 记录判过期)→ **恢复 2 条、丢弃 1 条
  stale**,`recoveries=2`,drain 后 2 completed;
- 损坏容错:4 行坏数据(垃圾行/未知 kind/非法优先级/字段缺失)只跳过坏行
  (`corrupt=3` 条合法计数),好记录不丢;写入 tmp+rename 原子替换、无 .tmp 残留。
