### HR-AUDIT-009 — Server-side protocol evidence

- **HTTP receipt contract (now implemented end-to-end)**: request = channel body JSON object (auto `targetId` + `sender_digests`); response = JSON (array or object), per-item `file` (verbatim echo, required), `status` ∈ `accepted|applied|failed` (+`reason`), optional `targetId` (mismatch → rejected), `digest` (applied requires frozen-sha256 equality), `note`, `revision` (number only). ## 6. HR-PR-04 increment (2026-11-13, save event pipeline pure core)

- `src/backend/hotReloadSavePipeline.ts` — pure core, no IO and no `vscode` import (clock, timers, snapshot read and syntax check are injected; the same boundary as `kode-vfs` VFS-001 and `hotReloadModuleIdentity`). The wiring side — vscode event binding, config faces, default switch — is not in this core.
- Per-file trailing debounce + global max-delay cap (HR-WATCH-006): a re-offer reschedules the window (true trailing debounce, not a fixed leading window) and the window budget is capped by `maxDelayMs`, so a save storm is deferred at most to `maxDelay` and never indefinitely. Cap truncation is recorded honestly as `max-delay-capped` on the event. The cap is enforced at scheduling time, not at due time: the trailing formula already bounds the timer at `first + maxDelay`, so a due-time check would be unreachable. The first window is capped too (`min(debounceMs, maxDelayMs)`), so `maxDelay < debounce` caps immediately.
- Event source coalescing (HR-WATCH-003/009): same canonical URI + same pending merge into one `FileChanged{uri,revision,diskHash,source,time}` with a coalesce reason; `disk-save-overlap` is only recorded in the save→disk-change direction (one write producing both events), and the representative source is the latest one.
- Write stability (HR-WATCH-007): two consecutive snapshot hashes must agree before sending; probe count is bounded (`maxStabilityProbes`), beyond which the last snapshot is sent honestly with an `unstable-after-N-probes` reason. Unreadable/deleted snapshots are dropped with a diagnostic, never guessed. A `settling` guard stops a second concurrent settle for the same URI while an async two-shot wait is in flight.
- Wave aggregation: files settled inside the same debounce window are merged into one batch (wave flush at `batchFlushMs`). Without a wave every settle passed exactly one event, so the HR-WATCH-016 threshold could never fire — the batch path was dead code.
- Dedupe key (HR-WATCH-010): canonical URI + targetId + content hash, reusing `canonicalizeScriptFilePath` from HR-PR-02 (so `file://` and bare-path forms of one file merge).
- Version guard (HR-WATCH-011): `revision` increments only when a new content version is actually emitted — dedupe and syntax blocks do not consume a number. Consuming one at offer time made an in-flight response for unchanged content look stale to `isStaleResponse(sent, current)`.

## 23. HR-STATE-012 storm-batching increment (2026-11-22, panel-open render/persist frequency cap)

## 24. HR-STATE-009 snapshot/current-state separation (2026-11-22, restart never trusts prior-session applied)

- The **history snapshot** is the only persisted hot-reload surface: `HotReloadHistoryCore` rows are written to `context.workspaceState` under `kbengine.hotReload.history` and reloaded at startup (HR-MOD-014), where entries whose shape does not match are dropped honestly. This is an append-only log of past operations — each row records the settled outcome of one request at one point in time, not a live claim about the file.
- The **current file state** is a separate, in-memory surface: the delivery ledger (`HotReloadTargetStateStore`) and the session baseline book (`HotReloadFileStateMachine`'s `baselines` map) are constructed fresh per extension host with no seed from persisted history. The per-file decorations and CodeLens (HR-UI-003/009) derive only from `stateMachine.derive(ledger, …)` — no current-state consumer reads the history log. A snapshot row showing `applied` therefore never becomes a live claim about the file's current state.
- Restart consequence: after a restart the ledger is empty and the baseline book is empty, so `derive` cannot attribute the file to any prior applied record. A file whose content still matches what was previously applied is treated as a **first-see** in this session (its current digest becomes the session baseline) and reports `CLEAN` — not `APPLIED`, and not `DIRTY` against a stale baseline either. The applied status can only be re-established by this session's own evidence: a new verified `applied` receipt, or (once wired) the engine-state query seam agreeing with a this-session ledger record's frozen `sentDigest`.
- The re-verification seam is honest and unwired: `engineAppliedDigestFor` (HR-STATE-003, `HotReloadFileStateMachine.deps`) is the sanctioned "re-verify the runtime revision" path, but it is not wired in production (the assembly currently provides only receipt evidence, per RUST-363's closure note). Even when wired it cannot resurrect applied on its own — it needs a this-session ledger record to compare the engine digest against, which a fresh session does not have. So the restart-never-trusts property holds today, and the re-verify capability is a named, tracked seam rather than an assumed active one.
- Tests: `tests/hotReloadFileState.test.ts` 5 pins — in-session applied trust (premise), restart re-deriving `CLEAN` with no verified hash and no timestamp for content that previously applied, restart with off-line content change staying `CLEAN` (fresh first-see baseline, no stale dirty), the engine seam without a this-session ledger record not resurrecting applied, and the two-surface separation (reloaded history keeps the `applied` row as fact while the current state reports `CLEAN`). ## 36. HR-EXT-005 isolated worker contribution (2026-11-22, RUST-409, budgeted dispatch + bounded backpressure)

- New versioned contribution face in the plugin-api core: `HotReloadWorkerAdapter` — a Python plugin (or fork) runs an **eligibility** and/or **response** adapter in an isolated worker (its own thread/process, off the extension host main thread). The core only defines the protocol and the budget; real worker-thread assembly is injected at wiring time via `dispatch`.
- Versioned message protocol: `HotReloadWorkerTask` (`kind` + `input`, with `HotReloadEligibilityInput` for eligibility / `HotReloadProviderInterpretInput` for response, plus an optional `correlationId`) → `HotReloadWorkerResult` (`ok=true` carries the decision/interpretation, `ok=false` carries the worker's own error). `HotReloadWorkerOutcome` is the honest three-state dispatch result: `resolved` / `timed-out` / `rejected`.
- **No unbounded blocking in the hot path** — the two bounds: ① `dispatchWorkerWithBudget` races the worker against a `budgetMs` timer and never waits past it; a worker that is still slow after the budget is reported `timed-out` and its late result is discarded (the slot is released at the budget, so a hung worker cannot hold capacity or block the save-event pipeline). ② `createHotReloadWorkerHost` enforces `maxInFlight` backpressure: at capacity a new task is `rejected` with `worker backpressure` instead of queueing unboundedly. `dispose` rejects any later dispatch.
- Adapter selection is by kind and first-match wins; an adapter that does not contribute the task's kind yields `rejected` `no adapter contributes <kind>` — the host never silently falls back, so a worker face is only used when something actually contributes it (otherwise the host's existing face runs).

## 37. HR-EXT-006 template as runtime adapter (2026-11-22, RUST-410, user-replaceable, no reload URL in Rust Core)

- The HTTP request template is now a **parameterized runtime-adapter implementation** rather than a hardcoded constant: `buildDefaultHotfixRequest(filePath, deps, moduleIdentity?, entry = BUILTIN_HTTP_REQUEST_EXAMPLE)` takes the template as its fourth parameter, and `DefaultHotfixSendDeps.template?` threads it into `sendDefaultHotfix`. A user's own `HttpRequestEntry` (the `kbengine.httpRequests` shape: url/method/headers/body) is therefore a drop-in replacement implementation — the `reload` URL lives only in the template (the TS-side single source), never in the Rust Core.
- New factory `createTemplateHotfixSendProvider(entry, deps)` builds a `HotReloadProvider` from any template; the built-in `createHttpHotfixSendProvider(deps)` is now a thin wrapper over that factory with the canonical id (`kbengine.http-hotfix`) and display name — the built-in is just the builtin template's adapter, not a special channel. A user template can replace it wholesale (registration order = answer order, so a fork-side template registered first wins).
- Permissions: a template adapter declares `['workspace', 'network']` like the built-in (it may probe package dirs for `${module}` and it sends) — no privilege exemption, same HR-EXT-004 discipline.
- Rust Core guarantee: `crates/` is the indexer/semantics/DB side and does not perform hot-reload HTTP.
