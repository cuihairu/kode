## 2. 阻塞缺陷与根因（上一轮,gdb 实测）

**现象**：baseapp 空闲（无 bots）时 `curl :8090/status` 4/4 次超时零字节;cellapp `:8091` 同时刻正常。监听 socket 存在、TCP 握手成功,进程不 accept/read。

**根因（gdb 线程栈）**：主线程 `epoll_wait` ← `EpollPoller::processPendingEvents` ← `EventDispatcher::processUntilBreak` ← `ServerApp::run`,全程握 GIL;Python 守护线程卡在 `PyEval_RestoreThread` → `pthread_cond_timedwait64`（等 GIL,cond=`_PyRuntime+1332`）。引擎源码 `kbe/src` **零** `Py_BEGIN_ALLOW_THREADS`/`PyEval_SaveThread`;唯一 `PyGILState_Ensure/Release`（`lib/pyscript/pythread_lock.h` `PyThreadStateLock`）只出现在 vcxproj,无任何实例化。GIL 只在主线程执行 Python 字节码时按 switch-interval 让出——空闲 baseapp 一条 Python 不跑 → HTTP 线程永久饿死。cellapp 健康是因为 Monster 0.5s AI 计时器周期性制造 GIL 窗口。

## 3. 上一轮两个修复尝试失败的真相（本轮补齐的诊断）

1. **脚本层 Python 异常并非不可见**。上一轮结论「脚本层异常无可见日志」是错的:引擎每进程 stdout/stderr 被 `run-demo-engine.sh` 重定向到 `$RUN_DIR/logs-proc/<app>.out`,未捕获异常带 `S_ERROR` 前缀落在那里;而脚本层 `print()` 走引擎 logger 面（log4cxx,本机不落盘）不可见,两者不是一条路。
2. **模块级 `KBEngine.addTimer` 心跳死于二进制/源码漂移**。`logs-proc/baseapp.out` 留下完整栈:

```
baseapp01: [S_ERROR]: Traceback (most recent call last):
  File ".../scripts/base/kbemain.py", line 52, in onInit
    KodeHotReload.start("base", bool(isReload))
baseapp01: [S_ERROR]:   File ".../scripts/common/KodeHotReload.py", line 364, in start
    start_heartbeat()
baseapp01: [S_ERROR]:   File ".../scripts/common/KodeHotReload.py", line 46, in start_heartbeat
    _heartbeat_timer = KBEngine.addTimer(HEARTBEAT_INTERVAL, HEARTBEAT_INTERVAL, heartbeat)
baseapp01: [S_ERROR]: AttributeError: module 'KBEngine' has no attribute 'addTimer'
```

   源码树 `python_app.cpp:723` 有 `__py_addTimer` + 模块方法表注册(:329),但本机二进制(2026-11-07 构建)的 `.rodata` 里没有 `__py_addTimer` 的报错格式串(`KBEngine::addTimer: '%.200s' object is not callable`),即**二进制早于该特性**——源码有、运行的二进制没有。上轮两个方案里真正该用的 API 是实体计时器。

## 4. 修复:实体计时器心跳（已交付,夹具+模板同步）
