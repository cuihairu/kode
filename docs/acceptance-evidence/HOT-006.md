日期：2026-11-15。任务：todo.md HOT-006「完整真实 KBEngine demo 验收 HTTP/xreload」。

## 3. 阻塞缺陷：base 侧接收器 wedge

**现象（可复现，4/4 次）**

```
$ curl -m 4 http://127.0.0.1:8090/status   # baseapp, 进程空闲(无 bots)
# 28 超时,零字节响应
$ curl -m 4 http://127.0.0.1:8091/status   # cellapp, 同一时刻
{"role": "cell", "pid": 3103150, "revision": 0, "receipts": []}   # 正常
```

baseapp 监听 socket 存在（`ss -ltn` 见 127.0.0.1:8090）、TCP 握手成功，但进程不再 accept/read 请求；`Recv-Q` 挂 2 条连接，`curl` 拿不到任何字节。曾有一次在战斗负载下 `/status` 成功（1.43s），此后 POST /hotfix 30s 返回空（`/tmp/hot006-receiptA-empty.json` 0 字节），`/status` 永久挂死。cellapp 8091 全程健康。

**根因（gdb 实测，非猜测）**

对 wedge 中的 baseapp 打线程栈：

| 线程 | 栈 |
|---|---|
| 主线程 | `epoll_wait` ← `EpollPoller::processPendingEvents` ← `EventDispatcher::processUntilBreak` ← `ServerApp::run` |
| Thread 2（Python 守护线程） | `_PyMethodDef_RawFastCallKeywords` → `PyEval_RestoreThread` → `__pthread_cond_timedwait64`（**卡在抢 GIL**，cond 在 `_PyRuntime+1332` = `gil`） |

全引擎源码（`kbe/src`）**没有任何** `Py_BEGIN_ALLOW_THREADS` / `PyEval_SaveThread` / `Py_BEGIN_ALLOW_THREADS`（grep 全树命中 0）；唯一的 `PyGILState_Ensure/Release` 在 `lib/pyscript/pythread_lock.h` 的 `PyThreadStateLock`，而该类**只在 vcxproj 里出现、无任何 .cpp 使用**——即从未被实际实例化。

推论：C++ 主线程在整个事件循环里握着 GIL，只在**执行 Python 字节码**时按 `sys.setswitchinterval`（默认 5ms）在 bytecode dispatch 检查点让出。空闲 baseapp（无实体计时器、无 bots）**一条 Python 都不跑** → HTTP 线程永远拿不到 GIL → 请求永不 accept。

cellapp 之所以健康：demo 的 `Monster` 跑 0.5s 循环 AI 计时器 → 主线程每 0.5s 执行 Python → 周期性 GIL 窗口。战斗期 baseapp 能跑一次 `/status`（reqAttack→cellAddExperience 频繁跑 Python）与同一机理吻合。

**已试的两个修复方向均未验证成功，不交付**

1. 实体计时器心跳（base/Spaces.py + cell/Space.py 挂 `addTimer(0.2,0.2)`，onTimer 内 `time.sleep(0.01)`）——已实现并同步模板，实测 base 8090 仍 4/4 超时，回滚。
2. 模块级 `KBEngine.addTimer(interval, repeat, cb)`（`python_app.cpp:721 __py_addTimer`，参数为 `(ffO)`）驱动的心跳，同样在 onInit 里调用——实测 base 8090 仍 4/4 超时，gdb 主线程仍在 epoll_wait 握 GIL，回滚。

**未决**：方案 2 是否真的没生效无法断定——引擎脚本层 Python 异常无可见日志（log4cxx 未配日志文件，`logs/` 目录为空，`logger` 进程无 .log 句柄），`KBEngine.addTimer` 若抛错会静默吞掉，从外面看不出心跳是否真的被注册。要确认得先解决脚本层日志可见性。

## 4. 附带发现：dbmgr 启动失败与脏库
