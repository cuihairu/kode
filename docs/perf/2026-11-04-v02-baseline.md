## 6. 宿主延迟综合

宿主事件循环阻塞段 = Provider 调用耗时(全部在宿主线程同步执行)。

| 场景 | 最坏交互(P95) | 最坏交互(max) | 主导项 |
|---|---|---|---|
| large-30k | 4.22ms(Definition py) | 9.53ms(Diagnostics 缺陷) | 全量 .py 扫描 10.4s(启动,后台) |
| multi-root | 10.94ms(Diagnostics def) | 26.72ms(Definition def) | 无(扫描仅 8.6ms) |
| big-py | 5.04ms(Completion py) | 13.53ms(Definition py) | 大文件 hover/补全 ~3.4-3.7ms(P50) |

**读法**:
1. **稳态交互全在亚毫秒~毫秒级**:large-30k 热态 P50 0.01-0.73ms,multi-root 0.01-0.87ms——
   30k 文件/多资产根不放大稳态交互(索引后台就绪,交互路径只付查询)。
2. **大 Python 文件是唯一显著交互放大**:big-py Hover P50 3.38ms、Completion(py) 3.67ms,
   为 large-30k 同维度(P50 0.13/0.06ms)的 ~26x / ~60x——8,000 方法单文件的局部变量
   上行推导与成员枚举是宿主阻塞大头。Definition(py) P99 10.66ms 亦显著高于 large。
3. **启动宿主成本**:large-30k 全量 .py 扫描 10.4s(激活期交互已可用,def 扫描仅 370ms
   即交互面就绪;30k .py 扫描是后台,不阻塞交互——见 §3.2 热态在扫描前即可用)。
4. **内存**:large-30k 扫描期 RSS +127.91MB(92.99→251.77MB);RSS 跨场景**不回落**
   (large 后驻留 ~252MB,big-py 前 ~269MB,JS 堆不返还 OS)——大仓首扫是内存大头。
5. **对照 KODE-PERF-006**:进程拓扑全量诊断(任一 def/清单变更触发的整拓扑重算)
   宿主同步阻塞 ~260ms @1000 def/2000 findings,是本树**最高的单次宿主阻塞**;
   本基线的交互面(单文档 Provider)全部 <27ms(max),差异即「单文件交互 vs 全局拓扑重算」。

## 7. 对照与限制

**对照(仅信息性,树已变不构成直接回归判定)**:
- 门1 基线(2026-10-23)冷 Hover P50 0.19ms / 热态命中 1 hit;本基线 large-30k 热态
  Hover P50 0.13ms 同量级(同机同口径)。
- PR1 冷扫描 S1 = 107,737ms → P0 修复后 4,880ms(10-23);本基线 large-30k 全量 .py
  扫描 10.4s——当前树扫描口径更宽(索引/缓存/多根/流敏感扩展),非同一口径,
  仅作形状参考。

**限制(如实声明)**:
- **fake-vscode 桩**:Provider 测量对桩工作区(stub workspaceFolders/findFiles),
  非真实 vscode 端到端;数字为相对量级,真实编辑器延迟含 IPC/渲染另有附加。
- **big-py Definition(def)=0 hit**(§5.1):该场景 entities.xml `<BigEntity>` → def
  未解析出位置(0 hit),该格数字为解析成本口径非命中口径;Definition 主维度以
  Definition(py)(全部场景 1 hit)为准。
- **冷态 py 交互 0 hit**:首扫在途索引未就绪,冷 py Hover/Completion 命中为 0——
  属预期(冷态口径是「首扫在途的交互成本」,非命中保证)。
- 进程拓扑全量诊断(KODE-PERF-006)不在本 bench,已单独测量(§6 对照引用)。
- bench 不进 pnpm test 门禁;本基线以「bench 跑完出数 + 报告落 doc」为准。
