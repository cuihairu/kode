# Kode — Player Data Clone (KBEngine Player Persistent Data Cloning) Detailed Implementation Plan

> Version: v1.0 (technical plan / Code Agent execution baseline)
> Date: 2026-11-05
> Target repo: [cuihairu/kode](https://github.com/cuihairu/kode)
> Status: design proposal; not a description of implemented features. This
> document relies on Kode's published README, the Cargo Workspace,
> `kode-types` source, and KBEngine documentation. Any specific database
> column name, child-table parent-child relation, and engine version
> behavior must be verified in Phase 0 against the target engine's source
> and real database-creation samples — never hard-coded from examples.

## 0. One-sentence conclusion

Build a **Rust-led Player Data Clone subsystem inside Kode**: use the
persistent database structure derived from the existing
`.def`/`types.xml`/`entities.xml` to **read-only export a specified player's
persisted Entities and their engine-generated child-table records** from an
authorized source MySQL database; produce an auditable, redactable,
verifiable offline archive; in a **stopped local test environment** preview
the impact, allocate new IDs, remap per known reference rules, import in a
transaction, and verify with a local engine load test.

**Explicitly not promised**: online authoritative memory snapshots,
automatic recognition of all business foreign keys, automatic cloning of an
entire game world, or automatic proof of reproduction of any live issue.

## 1. Requirements and non-goals

### 1.1 Core user stories

- The developer picks a project/Source Profile, an Entity type, a database
  interface, and a Player DBID, and sees the main and child tables that will
  be included.
- Clicking "one-click export": read-only, bounded copying of the character
  already persisted in the current database plus determinable child records,
  producing a re-importable package.
- Pick a local target environment: rehearse conflicts, unique-key problems,
  data redaction, account mapping, and ID rewriting.
- Clicking "one-click import": write only to targets explicitly marked
  local/test, generate new DBIDs and repair relations, run a local
  transaction; finally verify for real using KBEngine's native loading path.
- The mapping of original source DBIDs, types, and source version to new
  DBIDs is visible only in the authorized offline audit report, avoiding
  copying sensitive identity data.

### 1.2 Non-goals (v1)

- No reading transient in-memory objects from online BaseApp / CellApp; no
  calling `writeToDB()` to force online saves.
- No automatic copying of shared business entities such as guilds, friends,
  mail, leaderboards, or payment orders.
- No MySQL → PostgreSQL/MongoDB migration; no automatic migration of
  incompatible schemas.
- No direct online modification of a locally running, already loaded
  character; writes to online databases are not allowed.
- No universal SQL editor or production-account impersonation in the tool.

### 1.3 Export scope allowed for the MVP

1. A single Persistent Entity main table.
2. The `ARRAY`, component, and nested-container child tables determined by
   the engine's database mapper (the actual level the recursive `parentID`
   points at needs verification).
3. `FIXED_DICT` expanded fields within the same Entity and binary values
   exactly restorable.
4. Custom business associations do not follow by default; they extend only
   when the user explicitly specifies rules.
5. Exported objects must be persisted entities with stable database IDs;
   temporary entities are out of scope for this feature.

## 2. Fact baseline and source-code verification boundary

Kode's published README describes: a Rust Core (`kode-parser`, `kode-types`,
`kode-server`, etc.); database table-structure derivation, read-only table
preview, Schema Drift checks, isolated Profile connections, and table-name
prefix handling. The Cargo Workspace uses Rust 2021, minimum Rust 1.82,
`unsafe_code = forbid`. The existing `kode-types` provides an XML/def type
graph and container/alias/entity reference models.

**Still to verify**: whether the database table IR is provided directly by
Rust, whether the existing DB connector currently sits in TypeScript or
Rust, the actual SQL construction path, the engine branch and table-name
mapping, and the level-by-level linkage of `parentID` in real databases. The
README's listed features must not be treated as already covering
export/import.

KBEngine documentation confirms `Persistent=true` fields are archived, `tbl_`
is the common prefix for tables generated for business Entities/components/
custom types, `sm_` marks engine-managed fields; internal tables like `kbe_`
should not be copied by default. The documentation also warns that reading
the database directly is not equivalent to an online Entity's current values,
and a later online save may overwrite the database value.

### 3.1 Reducing duplicate implementation

- Reuse Kode's existing EntityDef and type graph; do not rewrite an XML
  parser.
- Use the existing Schema Drift capability to find mismatches between real
  and derived tables; **data cloning must fail closed on unconfirmed
  mappings**.
- If the existing database connection layer can be safely reused, reuse the
  connection configuration and TLS parsing; but create separate Export Read
  Sessions and Import Write Sessions.
- Do not lift Kode's current database panel's read-only restriction; writes
  go only through a dedicated local ImportExecutor and an explicit target
  permission boundary.

## 4. Schema / relation identification design

### 4.1 Two-level schema: derived + on-site verification

`DefDerivedSchema` comes from `.def`, `types.xml`, component definitions,
inheritance, and `Persistent` markers. `PhysicalSchema` reads actual
databases, columns, indexes, storage engines, primary keys, and auto-increment
info from MySQL `information_schema`. `ResolvedCloneSchema` contains only the
fields/relations matched on both sides and explicitly approved by rules.

- Table names, prefixes, component child tables, and container nesting paths
  must never be guessed by pure string splitting.
- Verify field data types, charsets, nullability, defaults, primary keys,
  and unique constraints.
- Original values are stored in **typed encodings**: unsigned integers,
  DECIMAL, DATETIME, BLOB, NULL, TEXT; converting all values to float64 /
  bare JSON numbers and back is forbidden.
- Explicit allow/deny policies are built separately for `kbe_` internal
  management tables and critical `sm_*` fields such as auto-login; whole-
  database scans are forbidden.

### 4.2 Relation classification (determines the degree of automation)

| Relation class | Example | v1 behavior |
|---|---|---|
| A engine-determined relations | entity main table → ARRAY/component child tables, `parentID` verified against the real engine | auto-discovered and copied |
| B real database constraints | FK present in INFORMATION_SCHEMA | shown in preview, copied when whitelisted |
| C explicit business relations | `Account` holds Avatar DBIDs, friend references | followed or rewritten only when the user declares rules |
| D unknown structure | IDs embedded in JSON/BLOB/Python custom objects | untouched by default, marked risky; plugin codecs if necessary |
| E external resources | Redis/payments/guilds/shared public-server state | out of MVP scope; a missing-report is provided |

**Key point**: if a nested child table's `parentID` points at the parent
ARRAY row's auto-increment ID rather than the player DBID, remapping must
recurse along a per-level relation graph. All primary keys and ID references
form typed mappings keyed by `{entityType, table, column, oldValue}`; global
`1001→5001` substitution is forbidden.

### 4.3 Relation-rule extension file (illustrative; not directly runnable)

```yaml
apiVersion: kode.dev/player-clone/v1alpha1
root:
  entity: Avatar
  lookup: dbid
relations:
  - name: account-avatar
    from: {entity: Account, property: characters}
    to: {entity: Avatar, key: databaseID}
    action: remap-if-present
    provenance: project-declared
  - name: guild-reference
    from: {entity: Avatar, property: guildDBID}
    action: detach-or-map-existing
    provenance: project-declared
identities:
  account: bind-existing-local-account
  loginCredentials: redact
  playerName: generate-unique-local
  autoLoad: disable
limits:
  maxRows: 50000
  maxBytes: 67108864
```

This is only the direction of a product DSL. Reference rules must compile,
verify fields really exist and have correct types; automatic callbacks
executing arbitrary SQL/Python scripts are forbidden.

## 5. Export design

### 5.1 Connections and authorization

- The Source Profile must explicitly set `source`,
  `environment=production|staging`; purpose is inferred from the database
  credential configuration, not the hostname.
- The source account is granted only SELECT on the needed schemas;
  UPDATE/INSERT/DELETE/DDL and any state repair against the source database
  are forbidden.
- Connection information goes in VS Code SecretStorage/the system credential
  service — never into the project's `.vscode/settings.json`, logs, or the
  archive.
- Prefer TLS, an SSH tunnel, or an intranet proxy to reach the read replica;
  automatically exposing the database port is forbidden.
- Use pre-approved Query Plans and parameterized DBID queries; physical
  identifiers must come from a verified schema allowlist.

### 5.2 Read-only consistency

- MySQL InnoDB, REPEATABLE READ + READ ONLY CONSISTENT SNAPSHOT, reading the
  main table and all child tables **within the same connection/transaction**;
  avoid reading the main table from version A and child tables from version B.
- `START TRANSACTION WITH CONSISTENT SNAPSHOT, READ ONLY` is used where
  supported; the actual transaction API must be checked against the driver's
  behavior.
- Only consistency of the committed database view can be guaranteed — not
  the latest state of Base/Cell online memory.
- Multiple DB interfaces, cross-instance, or non-transactional tables cannot
  get a globally consistent snapshot automatically; v1 should refuse to
  promise "fully consistent export" and annotate the limitation.
- Set timeouts, per-run row and size caps, and connection concurrency caps;
  end read transactions promptly to avoid InnoDB undo pressure; for oversized
  exports, run from a read replica or a test snapshot.

### 5.3 Export steps

1. Parse the project/engine version, entity type, and source database.
2. Check the user's authorization and purpose for exporting player data;
   collect operational audit metadata.
3. Build the main-child table relation plan from the DBID, identifying
   unknown business references and redacted fields.
4. Show a Dry Run: table list, estimated rows and size, sensitive fields,
   items that cannot be auto-copied.
5. In a read-only consistent transaction, run parameterized SELECTs and
   stream into a temporary archive; accumulating unbounded full results is
   forbidden.
6. Apply the specified redaction/exclusion policies to protected identity,
   credential, device-ID, social, and similar fields.
7. Generate the manifest, schema fingerprint, per-table record counts, and
   content checksums; encrypt the archive if needed.
8. Atomically rename after the archive completes; on interruption clean up
   the incomplete archive and audit the failure.

### 5.4 The Archive format

```text
avatar-<local-uuid>.kdpclone   # controlled archive container (zip-like or framed archive recommended)
├── manifest.json
├── data/
│   ├── tbl_Avatar.rows.cbor
│   └── tbl_Avatar_*.rows.cbor
├── relations.json
├── redaction-report.json
└── checksums.json
```

Prefer CBOR/MessagePack-style typed record encodings (or per-column
fixed-shape binary encodings), not a pure SQL dump — avoiding SQL injection,
type loss, and running unknown scripts at import. The manifest must contain
at least: archiveVersion, engineVariant/version, projectRevision, Entity/
typeDefs hashes, DB schema fingerprint, database interface, capture time/
consistency mode, protected identifiers of the root Entity/DBID, included and
excluded tables, redaction policy version, original type metadata, and file
SHA-256. Archives are encrypted by default, with the key never stored
alongside the archive; syncing to cloud drives or Git by default is
forbidden.

## 6. Import and ID remapping

### 6.1 Safety gates

- The target connection must explicitly declare `environment=local|test`;
  prod/staging targets are forbidden. Judging safety by `127.0.0.1` alone is
  unreliable.
- Require first that the KBEngine local target instance is stopped / the
  target Entity is not checked out; detecting local processes and DBMgr
  state may be added.
- Support both "empty target database + keep original DBIDs" and "existing
  test database + new DBIDs", but recommend new-ID mode by default to reduce
  collision risk.
- Force a rehearsal of unique-key/account conflicts, charset and data-type
  compatibility, engine version differences, auto-load switches, and
  external associations.
- No automatic table creation/DDL on the target. The target's table
  structure should first be created by the corresponding KBEngine engine
  version.

### 6.2 Two-phase commit-style planning (not a distributed two-phase commit)

**Prepare:** load and verify the Archive → compare target schemas → sort the
relation DAG → generate a typed IDMap → unique-key strategy/account
binding/sensitive-field handling → output a fully auditable SQL plan
(parameter placeholders, not raw sensitive values).

**Apply:** within a **single transaction** on local MySQL InnoDB: insert each
Entity's main row → get the new primary key → insert child tables per
dependency order → get intermediate row keys and update parentIDs level by
level → handle explicit business references → disable online autoLoad →
check row counts, main-child relations, and constraints → COMMIT; ROLLBACK
on failure. Sequence gaps from MySQL `AUTO_INCREMENT` cannot be rolled back,
which does not affect the transactional atomicity of data rows. With
multiple DBs/non-transactional tables, v1 must not claim atomic import.

**Verify:** after import, read-only checks of target row counts/hashes/
reference relations; optionally start local KBEngine and load with the
standard `createEntityFromDBID`, verifying login or Entity properties. A
load failure must not casually delete committed data — return a cleanable
local import inventory and wait for the user.

### 6.3 Concrete IDMap requirements

- Distinguish `runtime entity.id`, `Entity.databaseID`, child-table row IDs,
  custom business IDs, and third-party account IDs.
- The `oldID → newID` key includes the database interface, Entity type,
  physical table, and primary-key column, so repeated numbers in different
  tables are never cross-contaminated.
- New primary keys come from the database after the target insert; all
  related fields use mapping results, never arithmetic offsets.
- Business-permanently-stable item template IDs, skill config IDs, and map
  IDs are not rewritten.
- Unique fields such as usernames, nicknames, and account names get locally
  unique generated values per configuration, with uniqueness checks.
- The `Account`↔`Avatar` relation depends on the project's real
  implementation: without a mapping rule, importing an Avatar will not
  automatically make a local account see the character — the UI must state
  this explicitly.
- Old player data carries no real tokens, password hashes, or payment/device
  identity; account binding happens within the local security policy.

### 6.4 Re-import and rollback

- Use the archive hash + importRun ID to check for duplicate operations;
  by default show the already-imported mapping and do not create the
  character again; allow the user to explicitly choose "create another copy".
- Before-commit failures roll back the transaction; after-commit failures
  provide a **local-only** controlled cleanup inventory, never implicitly
  replaying deletions.
- Cleanup must detect whether the entity was already loaded by the local
  game server and whether other test data references it.
- Cancellation support: Prepare can be cancelled anytime; cancelling Apply
  rolls back; Verify can be aborted without erasing import results.

## 7. VSCode product design

A new Explorer group `Player Data Clone`:

1. **Connections**: two Profiles — Source (read-only) and Target (locally
   writable) — TLS/SecretStorage, connection testing and version info.
2. **Export Player Data**: Entity type selection, DBID entry/search
   (authorized search only), export scope selection, relation explanations.
3. **Export Preview**: estimated data volume, table/row counts, schema
   drift, sensitive information, business relations to be skipped, and the
   consistency level.
4. **Archive Browser**: open `.kdpclone`, showing anonymized player refs,
   included fields, hashes, source version, redaction status; passwords/
   tokens not shown by default.
5. **Import Preview**: target environment, account binding policy,
   keep/new IDs, unique-key conflicts, possibly unreproducible issues, Dry
   Run.
6. **Import Results**: new DBIDs, table-level record counts, relation
   verification, error location and one-click copy of non-sensitive logs;
   optional `Open Entity in Local KBEngine`.

Suggested command names:

- `KBEngine: Export Persistent Entity`
- `KBEngine: Preview Player Clone`
- `KBEngine: Import Player Clone`
- `KBEngine: Verify Imported Entity`
- `KBEngine: Show Clone Audit`

**Interaction constraints**: the UI says "a copy of the database's persisted
data", never "the complete online current state"; if business reference
mappings are missing, the export can continue but the import must first
explain which parts will be missing.

## 8. CLI and Rust API contract draft

```bash
kode-db-clone inspect --project ./server_assets --entity Avatar
kode-db-clone plan-export --source source-profile --entity Avatar --dbid 1234 --out plan.json
kode-db-clone export --plan plan.json --out avatar.kdpclone
kode-db-clone inspect-archive avatar.kdpclone
kode-db-clone plan-import --archive avatar.kdpclone --target local-profile --policy ./clone-policy.yaml
kode-db-clone import --plan import-plan.json --confirm-local
kode-db-clone verify --run <import-run-id> --target local-profile
```

CLI examples are not commands that exist today; the real implementation
should avoid passing passwords on the command line, supporting stdin/
SecretStorage/environment credentials and structured JSON output.
Experimental or scripted output must not contain raw player privacy data.

Rust type interface sketch:

```rust
struct CloneContext { source_schema: ResolvedSchema, target_schema: ResolvedSchema }
struct ExportPlan { root: EntityKey, table_queries: Vec<ApprovedSelect>, limits: Limits }
struct ImportPlan { table_inserts: Vec<TypedInsert>, remap_policy: RemapPolicy }
struct CloneArchive { manifest: Manifest, records: Vec<TypedRecord> } // actual import needs streaming reads

trait SourceReader { /* read-only snapshot + parameterized SELECT only */ }
trait TargetWriter { /* local-only transaction/insert/rollback */ }
```

Interfaces should have hard resource budgets and explicit error types
(UnsupportedMapping, SchemaMismatch, SourceNotReadOnly, TargetNotLocal,
DuplicateIdentity, UnresolvedReference, ExportTruncated, ImportFailed,
VerificationFailed).

## 11. Definition of Done

The MVP counts as done only when all of the following hold:

1. An end-to-end demonstration of a single Avatar (including ARRAY/
   components) export and local import, using test MySQL tables actually
   auto-generated by KBEngine, not hand-written fakes.
2. The source database read-only; exporting multiple related tables with
   InnoDB consistent reads; the archive carries type info, hashes, versions,
   and a redaction report.
3. The target is a defined local environment; a Dry Run is shown before
   import; new IDs, recursive parentID mapping, unique-key conflicts, and
   transaction rollback supported.
4. The imported Avatar can be loaded via the target KBEngine's native API;
   if account binding is unsupported, it is explicitly disclosed.
5. The open-source repo carries complete golden/integration/failure-injection/
   security tests and a reproducible tutorial.
6. No exaggerated claims like "automatically copying the complete online
   current state" or "automatically understanding all player business
   relations".

## 12. Technical risks and trade-offs

- **Highest risk: misjudging engine mappings.** Lock relations with actual
  engine C++ source and real table-creation samples; never infer from
  naming.
- **High risk: business IDs.** Automatic handling limited to engine-
  determinable parent-child relations; business references must be explicit
  declarations.
- **High risk: privacy and accounts.** Copying credentials/payment info is
  forbidden by default; archives redacted + encrypted; accounts bound
  locally.
- **High risk: source database vs live memory divergence.** The UI always
  marks Persisted Clone; for the latest memory state, design a separate
  controlled server export — out of the current project.
- **High risk: target engine version differences.** V1 supports only
  structure-exact compatibility; schema migration is a separate capability.
- **Medium risk: target writes affecting the online game.** The local
  service must be stopped by default; online hot injection refused.
- **Medium risk: long transactions crushing the production database.**
  Budget limits, batched reads, short timeouts; prefer read replicas.
- **Medium risk: account/character identity binding.** Most business logic
  is project-custom; `.def` cannot automatically reveal all ownership rules.

## 13. Priority and iteration advice

### v0.1 the verifiable core (first)

- Precise export of the real main table and one level of ARRAY/component
  tables, offline archive, restore into an empty local database.
- Read-only safety, schema verification, level-by-level parentID rewriting,
  transactional import, native Entity load verification.
- One complete CLI test chain; a command-palette entry inside Kode first.

### v0.2 daily usable

- Full nested relations, project business reference rules, local account
  binding, ID remapping into an existing test database.
- Visual previews, conflict and permission controls, data redaction/
  encryption, regression tests.

### v0.3 later extensions (per actual need)

- Multiple anonymized test copies from one archive, relation templates,
  post-import diff diagnostics.
- Differential adaptation across KBEngine branches/projects; more database
  backends need separate evaluation.

**Do not do**: whole-server/whole-database migration from the start,
automatically tracking all EntityCalls and arbitrary Python objects, or
turning Kode into a game GM platform.
