# Kode — Player Data Clone（KBEngine 玩家持久化数据克隆）详细实施计划书

> 版本：v1.0（技术方案/Code Agent 执行基线）  
> 日期：2026-11-05  
> 目标仓库：[cuihairu/kode](https://github.com/cuihairu/kode)  
> 状态：设计提案；非已实现功能说明。本文以 Kode 已公开的 README、Cargo Workspace、`kode-types` 源码及 KBEngine 文档为依据。任何具体数据库列名、子表父子关系和引擎版本行为，都必须在 Phase 0 用目标引擎源码与实际建库样本验证，不能仅凭示例硬编码。

## 0. 一句话结论

在 **Kode 内实现一个 Rust 主导的 Player Data Clone 子系统**：利用现有 `.def`/`types.xml`/`entities.xml` 派生的持久化数据库结构，从已授权的源 MySQL 数据库**只读导出指定玩家的已持久化 Entity 及其引擎生成的子表记录**；生成可审计、可脱敏、可校验的离线归档；在**已停止的本地测试环境**中预览影响、分配新 ID、按已知引用规则重映射、事务导入，并用本地引擎加载测试验证。

**明确不承诺**在线权威内存快照、自动识别所有业务外键、自动克隆整个游戏世界，或自动证明重现任何线上问题。

## 1. 需求与非目标

### 1.1 核心用户故事

- 开发者选择项目/Source Profile、Entity 类型、数据库接口及 Player DBID，查看将包含的主表和子表。
- 点击“一键导出”：只读、限量地复制当前数据库里已经持久化的角色及可确定的子记录，生成一个可重复导入的包。
- 选择本地目标环境：预演冲突、唯一键问题、数据脱敏、账号映射及 ID 重写。
- 点击“一键导入”：仅对明确标记为 local/test 的目标写入，生成新 DBID 并修复关系，执行本地事务；最后使用 KBEngine 原生加载路径进行真实验证。
- 原始源 DBID、类型、源版本与新 DBID 的映射仅在授权的离线审计报告中可见，避免复制敏感身份数据。

### 1.2 非目标（v1）

- 不从在线 BaseApp / CellApp 读取瞬时内存对象；不调用 `writeToDB()` 强制线上存档。
- 不自动复制公会、好友、邮件、排行榜、支付订单等共享业务实体。
- 不迁移 MySQL → PostgreSQL/MongoDB，不自动迁移不兼容 Schema。
- 不直接在线修改本地正在运行并已载入的角色，不允许向线上数据库写入。
- 不在工具内提供万能 SQL 编辑器或生产账号 impersonation。

### 1.3 MVP 允许的导出范围

1. 单个 Persistent Entity 主表。
2. 由引擎的数据库映射器确定的 `ARRAY`、组件、嵌套容器子表（需要核实递归 `parentID` 实际指向哪个层级主键）。
3. 同一个 Entity 内的 `FIXED_DICT` 展开字段和可精确还原的二进制值。
4. 自定义业务关联默认不跟随；用户明确指定规则才扩展。
5. 导出的对象需要是有稳定数据库 ID 的持久化实体；临时 Entity 不属于此功能。

## 2. 事实基线与源代码核验边界

Kode 已公开的 README 描述：Rust Core（`kode-parser`、`kode-types`、`kode-server` 等）；数据库表结构推导、只读表预览、Schema Drift 检查、隔离 Profile 连接及表名前缀处理。Cargo Workspace 采用 Rust 2021、最低 Rust 1.82、`unsafe_code = forbid`。现有 `kode-types` 提供 XML/def 类型图与容器/别名/实体引用模型。

**必须继续核实**：数据库表 IR 是否由 Rust 直接提供、现有 DB connector 目前处于 TypeScript 还是 Rust、实际 SQL 构建路径、引擎分支与表名映射、真实数据库中 `parentID` 的逐级关联。不能将 README 中列出的功能当成已覆盖导出/导入。

KBEngine 文档确认 `Persistent=true` 字段被存档，`tbl_` 为业务 Entity/组件/自定义类型生成表的常见前缀，`sm_` 为引擎管理字段；`kbe_` 一类内部表不应默认复制。文档也警示直接读取数据库不能等同在线 Entity 当前值，在线 Entity 后续存档可能覆盖库中值。

## 3. 方案架构

```text
VSCode Kode UI (TypeScript)
  ├── Source Profile / Player Picker / Export Plan Preview
  ├── Archive Preview / Target Profile / Import Plan Preview
  └── 只负责交互、取消、审计展示，不持有写入业务规则
              │ 版本化、有限能力的命令协议
              ▼
Rust Core (现有 schema/type 层复用)
  ├── kode-db-clone (新 crate)
  │    ├── SchemaResolver        结构映射、源/目标 Drift 检查
  │    ├── RelationGraph         引擎子表关系 / 显式业务关系
  │    ├── ExportPlanner         可导出范围、SQL 查询计划
  │    ├── ExportExecutor        源库只读一致性快照 / 流式读取
  │    ├── ArchiveCodec          归档、校验、加密、脱敏
  │    ├── ImportPlanner         目标差异、唯一键冲突、ID 重映射计划
  │    ├── ImportExecutor        目标库事务写入
  │    └── ImportValidator       数据关系验证与加载结果
  ├── kode-parser / kode-types  (现有)
  └── kode-server                 (沿用已有 LSP，不让普通 LSP 查询获得写权限)
              │
     SourceReader (强制只读)      TargetWriter (只允许 local/test)
              │                           │
      源 MySQL / read replica           本地 MySQL
```

### 3.1 减少重复实现

- 复用 Kode 现有 EntityDef 与类型图，不重新编写 XML 解析器。
- 用既有 Schema Drift 能力发现真实表与推导表不一致；**数据克隆对未确认的映射必须 fail closed**。
- 若现有数据库连接层可安全复用，则复用连接配置和 TLS 解析；但创建独立的 Export Read Session 与 Import Write Session。
- 不解除 Kode 当前数据库面板的只读限制；写操作只能走专门的本地 ImportExecutor 和显式的目标权限边界。

## 4. Schema / 关系识别设计

### 4.1 两级 Schema：推导 + 现场校验

`DefDerivedSchema` 来自 `.def`、`types.xml`、组件定义、继承、`Persistent` 标记。`PhysicalSchema` 从 MySQL `information_schema` 读取实际库表、列、索引、存储引擎、主键、自增信息。`ResolvedCloneSchema` 只包含两侧匹配并经规则明确批准的字段/关系。

- 表名称、前缀、组件子表、容器嵌套路径不得基于纯字符串拆分猜测。
- 校验字段数据类型、字符集、可空性、默认值、主键和唯一约束。
- 原始值用**有类型的编码**保存：无符号整数、DECIMAL、DATETIME、BLOB、NULL、TEXT；禁止所有值转 float64 / 纯 JSON 数字后再导回。
- `kbe_` 内部管理表、自动登录等关键 `sm_*` 字段分别建立显式 allow/deny 策略，禁止整库扫描。

### 4.2 关系分类（决定自动化程度）

| 关系类别 | 例子 | v1 行为 |
|---|---|---|
| A 引擎确定关系 | 实体主表 → ARRAY/组件子表、经真实引擎核实的 `parentID` | 自动发现与复制 |
| B 真实数据库约束 | INFORMATION_SCHEMA 有 FK | 显示预览，符合白名单时复制 |
| C 显式业务关系 | `Account` 持有 Avatar DBID、好友引用 | 用户声明规则才跟随或重写 |
| D 不明结构 | JSON/BLOB/Python 自定义对象中嵌 ID | 默认不改、标风险，必要时通过插件 codec |
| E 外部资源 | Redis/支付/公会/公服共享状态 | 不属于 MVP，提供缺失报告 |

**关键：** 若嵌套子表的 `parentID` 指向上一级 ARRAY 行的自增 ID，而非玩家 DBID，必须按逐层关系图递归重映射。所有主键及 ID 引用按 `{entityType, table, column, oldValue}` 形成有类型的映射，禁止全局 `1001→5001` 替换。

### 4.3 关系规则扩展文件（示意，不可直接运行）

```yaml
apiVersion: kode.dev/player-clone/v1alpha1
root:
  entity: Avatar
  lookup: dbid
relations:
  - name: account-avatar
    from: {entity: Account, property: characters}
    to: {entity: Avatar, key: databaseID}
    action: remap-if-present
    provenance: project-declared
  - name: guild-reference
    from: {entity: Avatar, property: guildDBID}
    action: detach-or-map-existing

```

这只是产品 DSL 方向。引用规则需编译、验证字段真实存在及类型正确，禁止提供任意 SQL/Python 脚本执行的自动回调。

## 5. 导出设计

### 5.1 连接与授权

- Source Profile 必须显式设置 `source`, `environment=production|staging`；以数据库凭据配置而非主机名推断用途。
- 源账号仅授予所需 schema 的 SELECT 权限；禁止 UPDATE/INSERT/DELETE/DDL 和向源库执行任何状态修复。
- 连接信息放 VS Code SecretStorage/系统凭据服务，不能写入项目 `.vscode/settings.json`、日志或归档。
- 优先通过 TLS、SSH Tunnel 或内网代理访问只读副本，禁止自动暴露数据库端口。
- 使用预先批准的 Query Plan 和参数化 DBID 查询；物理标识符必须来自受校验的 Schema allowlist。

### 5.2 只读一致性

- MySQL InnoDB、REPEATABLE READ + READ ONLY CONSISTENT SNAPSHOT，在**同一连接/事务**内读取主表和所有子表；避免主表读自版本 A、子表读自版本 B。
- `START TRANSACTION WITH CONSISTENT SNAPSHOT, READ ONLY` 在支持条件下使用；实际事务 API 要检查库驱动行为。
- 仅能保证已提交数据库视图的一致性，不保证 Base/Cell 在线内存的最新状态。
- 多 DB 接口、跨独立实例或非事务表无法自动获得全局一致快照，v1 应拒绝“完整一致导出”承诺并标注局限。
- 设置超时、单次行数与体积上限、连接并发上限，及时结束读事务以避免 InnoDB undo 压力；导出过大时建议从只读副本或测试快照运行。

### 5.3 导出步骤

1. 解析项目/引擎版本、实体类型、源数据库。
2. 检查用户对玩家数据导出的授权和目的；收集操作审计元信息。
3. 根据 DBID 构建主子表关系计划，识别未知业务引用与脱敏字段。
4. 展示 Dry Run：表清单、预计行数和体积、敏感字段、无法自动复制项。
5. 在只读一致性事务中执行参数化 SELECT，流式写临时归档；不得无上限累积完整结果。
6. 对受保护的身份、凭据、设备 ID、社交等字段执行指定脱敏/排除策略。
7. 生成 manifest、Schema 指纹、逐表记录数和内容校验；必要时归档加密。
8. 完成归档后原子重命名；中断时清理不完整归档并审计失败。

### 5.4 Archive 格式

```text
avatar-<local-uuid>.kdpclone   # 受控归档容器（建议 zip-like 或 framed archive）
├── manifest.json
├── data/
│   ├── tbl_Avatar.rows.cbor
│   └── tbl_Avatar_*.rows.cbor
├── relations.json
├── redaction-report.json
└── checksums.json
```

建议用 CBOR/MessagePack 风格的类型化记录编码（或逐列定型的二进制编码），不要纯 SQL Dump，避免 SQL 注入、类型丢失、导入时直接运行未知脚本。Manifest 至少包含：archiveVersion、engineVariant/version、projectRevision、Entity/typeDefs 哈希、DB schema fingerprint、数据库接口、捕获时间/一致性模式、root Entity/DBID 的受保护标识、包含与排除表、脱敏策略版本、原始类型元数据、文件 SHA-256。默认加密归档，秘钥不跟归档同存；禁止默认同步到云盘或 Git。

## 6. 导入与 ID 重映射

### 6.1 安全门槛

- 目标连接必须显式声明 `environment=local|test`；禁止 prod/staging 目标。仅靠 `127.0.0.1` 判断安全不可靠。
- 先要求 KBEngine 本地目标实例已停止/目标 Entity 未被检出；可增加检测本地进程和 DBMgr 状态。
- 支持“空白目标数据库 + 保留原 DBID”与“已有测试库 + 新 DBID”两模式，但默认建议新 ID 模式，降低碰撞风险。
- 强制预演唯一键/账号冲突、字符集和数据类型兼容、引擎版本差异、自动加载开关、外部关联。
- 不对目标做自动建表/DDL。目标应先由对应版本 KBEngine 引擎创建正确表结构。

### 6.2 两阶段提交式规划（不是分布式两阶段提交）

**Prepare：** 加载并验证 Archive → 对比目标 Schema → 关系 DAG 排序 → 生成 typed IDMap → 唯一键策略/账号绑定/敏感字段处理 → 输出完全可审计的 SQL 计划（参数占位而非原始敏感值）。

**Apply：** 在本地 MySQL InnoDB 的**单个事务**中：插入各 Entity 主行 → 获得新主键 → 按依赖关系插入子表 → 获得中间行主键并逐级更新 parentID → 处理明确业务引用 → 禁用线上 autoLoad → 检查行数、主子关系和约束 → COMMIT；失败 ROLLBACK。MySQL `AUTO_INCREMENT` 产生的序列间隙不可回滚，这不影响数据行的事务原子性。若多 DB/非事务表，v1 禁止宣称原子导入。

**Verify：** 导入后只读核对目标 row count/hash/引用关系；可选启动本地 KBEngine，使用标准 `createEntityFromDBID` 加载，验证登录或 Entity 属性。加载失败不能随意删除已提交的数据，返回可清理的本地导入清单并等待用户操作。

### 6.3 IDMap 具体要求

- 区分 `runtime entity.id`、`Entity.databaseID`、子表行 ID、自定义业务 ID、第三方账号 ID。
- `oldID → newID` 键包含数据库接口、Entity 类型、物理表和主键列，避免不同表编号重复被串改。
- 新主键在目标插入后由数据库返回，所有相关字段使用映射结果而非算数偏移。
- 业务上永久稳定的物品模板 ID、技能配置 ID、地图 ID 不重写。
- 用户名、昵称、账号名等唯一字段按配置生成局部唯一值并验重。
- 对 `Account` 与 `Avatar` 的关系依赖项目真实实现：若没有映射规则，导入 Avatar 并不能自动让本地账号看到该角色，UI 必须明确提示。
- 旧玩家数据不携带真实令牌、密码 hash、支付/设备身份信息；账号绑定必须在本地安全策略内进行。

### 6.4 重复导入与回滚

- 用 archive hash + importRun ID 检查重复操作，默认显示已导入映射，不再重复创建角色；允许用户明确选择“另建副本”。
- 失败前未提交时事务回滚；提交后失败时提供**仅本地**受控 cleanup 清单，不隐式重放删除。
- 清理必须检测该实体是否已由本地游戏服务器加载及是否被其他测试数据引用。
- 支持取消：Prepare 可随时取消，Apply 取消则 rollback，Verify 可中止而不抹除导入结果。

## 7. VSCode 产品设计

新增 Explorer 分组 `Player Data Clone`：

1. **Connections**：Source（只读）和 Target（本地可写）两条 Profile，TLS/SecretStorage，测试连接和版本信息。
2. **Export Player Data**：Entity 类型选择、DBID 输入/搜索（仅授权搜索）、选择导出范围、关联关系说明。
3. **Export Preview**：预估数据量、表/行数量、Schema 漂移、敏感信息、将跳过的业务关系和一致性等级。
4. **Archive Browser**：打开 `.kdpclone`，显示匿名化 player ref、包含字段、Hash、源版本、脱敏状态；默认不展示密码/token。
5. **Import Preview**：目标环境、账号绑定策略、保留/新建 ID、唯一键冲突、可能无法重现的问题、Dry Run。
6. **Import Results**：新 DBID、表级记录数、关系校验、错误定位与一键复制非敏感日志；可选 `Open Entity in Local KBEngine`。

建议命令名称：

- `KBEngine: Export Persistent Entity`
- `KBEngine: Preview Player Clone`
- `KBEngine: Import Player Clone`
- `KBEngine: Verify Imported Entity`
- `KBEngine: Show Clone Audit`

**交互约束：** UI 显示“数据库已持久化数据副本”，不要称作“在线当前完整状态”；如果缺业务引用映射，导出可以继续但导入前需要说明会缺失哪些部分。

## 8. CLI 与 Rust API 契约草案

```bash
kode-db-clone inspect --project ./server_assets --entity Avatar
kode-db-clone plan-export --source source-profile --entity Avatar --dbid 1234 --out plan.json
kode-db-clone export --plan plan.json --out avatar.kdpclone
kode-db-clone inspect-archive avatar.kdpclone
kode-db-clone plan-import --archive avatar.kdpclone --target local-profile --policy ./clone-policy.yaml
kode-db-clone import --plan import-plan.json --confirm-local
kode-db-clone verify --run <import-run-id> --target local-profile
```

CLI 示例不等于现在存在的命令；正式实现应避免在命令行参数中传递密码，支持 stdin/SecretStorage/环境凭据与结构化 JSON 输出。实验或脚本输出中不可包含原始玩家隐私数据。

Rust 类型接口示意：

```rust
struct CloneContext { source_schema: ResolvedSchema, target_schema: ResolvedSchema }
struct ExportPlan { root: EntityKey, table_queries: Vec<ApprovedSelect>, limits: Limits }
struct ImportPlan { table_inserts: Vec<TypedInsert>, remap_policy: RemapPolicy }
struct CloneArchive { manifest: Manifest, records: Vec<TypedRecord> } // 实际导入需流式读取

trait SourceReader { /* read-only snapshot + parameterized SELECT only */ }
trait TargetWriter { /* local-only transaction/insert/rollback */ }
```

接口应有硬性资源预算、明确错误类型（UnsupportedMapping、SchemaMismatch、SourceNotReadOnly、TargetNotLocal、DuplicateIdentity、UnresolvedReference、ExportTruncated、ImportFailed、VerificationFailed）。

## 11. 完成定义（Definition of Done）

MVP 仅在以下全部成立时视为完成：

1. 使用真实 KBEngine 自动生成的测试 MySQL 表，而非手写假表，端到端演示单个 Avatar（含 ARRAY/组件）的导出和本地导入。
2. 源库只读，导出多个关联表时具有 InnoDB 一致性读取；归档有类型信息、Hash、版本、脱敏报告。
3. 目标为确定的本地环境、导入前展示 Dry Run，支持新 ID、递归 parentID 映射、唯一键冲突、事务回滚。
4. 可用目标 KBEngine 原生 API 加载导入的 Avatar；账号绑定如果不支持就显式告知。
5. 开源仓库包含完整 Golden/集成/失败注入/安全测试和可复现教程。
6. 没有任何“自动复制线上当前完整状态”或“自动理解所有玩家业务关系”的夸大表述。

## 12. 技术风险与取舍

- **最高风险：引擎映射误判。** 用实际引擎 C++ 源码和真实建库样本锁定关系，不能根据命名推断。
- **高风险：业务 ID。** 自动处理仅限引擎可确定的父子关系；业务引用必须通过显式声明。
- **高风险：隐私与账号。** 默认禁止复制凭据/支付信息，归档脱敏+加密，绑定本地账号。
- **高风险：源库与运行内存不一致。** UI 永远标记 Persisted Clone；如需最新内存状态，另行设计受控服务器导出，不纳入当前项目。
- **高风险：目标引擎版本差异。** V1 只支持结构精确兼容，Schema migration 是独立能力。
- **中风险：目标库写入影响在线游戏。** 默认要求本地服务停止，拒绝在线热注入。
- **中风险：长事务压垮生产数据库。** 预算限制、分批读取、短超时，优先只读副本。
- **中风险：账号/角色身份绑定。** 多数业务逻辑是项目自定义，不可通过 `.def` 自动了解全部所有权规则。
