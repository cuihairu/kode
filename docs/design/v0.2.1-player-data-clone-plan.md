# Kode — Player Data Clone 项目实施计划

**项目归属：** cuihairu/kode  
**核心技术：** Rust + MySQL + VSCode Extension  
**项目目标：** 基于 KBEngine 的持久化数据模型，实现玩家数据的一键导出、ID 重映射、本地导入和调试验证。

## 1. 产品目标

开发者能够从已授权的线上数据库选择一个玩家，自动提取该 Entity 的持久化数据及引擎生成的关联子表，保存成独立归档，再导入本地开发数据库。

导入时可以根据目标环境自动分配新的数据库 ID、重建主子表关系，并按配置将角色绑定到本地测试账号。

第一版仅复制已持久化的数据，不尝试抓取 BaseApp 或 CellApp 中尚未存档的实时内存状态。

## 2. 设计原则

- 复用 Kode 现有的 Rust 类型图和数据库结构推导。
- 不重新编写 KBEngine 的 XML、DEF 解析器。
- 源数据库强制只读，目标数据库只允许明确授权的本地测试环境。
- 自动处理能够从引擎存储映射中确定的主子表关系。
- 业务自定义引用必须通过显式规则处理，不根据字段名称猜测。
- 导入前必须展示完整执行计划。
- 使用数据库事务保证受支持的导入操作原子性。
- 保证数据类型精度和二进制内容不丢失。

## 3. Rust 模块划分

新增 `kode-db-clone` Crate，包括：

| 模块 | 职责 |
|---|---|
| SchemaResolver | 合并 DEF 推导结构与真实数据库结构 |
| RelationGraph | 识别 Entity、组件、ARRAY 等关系 |
| ExportPlanner | 生成只读导出查询计划 |
| ExportExecutor | 一致性读取及流式导出 |
| ArchiveCodec | 数据归档、校验、脱敏与加密 |
| ImportPlanner | 检查冲突并生成导入计划 |
| IDMapper | 新旧 ID 映射及关联修复 |
| ImportExecutor | 本地事务导入 |
| ImportValidator | 导入结果检查及 KBEngine 加载验证 |

原有 Kode 数据库预览功能保持只读，不将普通数据库查询入口升级为通用写入接口。

## 4. 数据导出

以 Entity 类型与 DBID 为入口：

1. 检查源数据库连接和 Entity 定义。
2. 读取实际表结构并与 Kode 的推导结果对比。
3. 找到 Entity 主表及引擎管理的关联子表。
4. 计算导出范围、预计记录数和数据量。
5. 按 MySQL 一致性读取规则获取已提交的数据。
6. 对敏感字段执行脱敏或排除策略。
7. 保存为版本化的离线归档。
8. 生成记录数量、Schema Hash 和完整性校验信息。

导出时不调用线上 Entity 的存档函数，也不修改线上业务状态。

## 5. 数据归档

归档应包含：

- 引擎分支与版本。
- Entity 类型和源数据库接口。
- DEF、类型定义以及数据库结构指纹。
- 完整的主表和子表记录。
- 类型信息、二进制字段和 NULL 信息。
- 关联关系定义。
- 敏感字段处理结果。
- 原始数据校验值。

数据应采用有类型的二进制编码，而不是简单将所有 SQL 列转换成 JSON 数字或字符串。

## 6. ID 重映射

必须区分：

- Entity 运行时 ID。
- Entity 的数据库 ID。
- ARRAY 等子表自身的行 ID。
- 子表 `parentID`。
- Account 与 Avatar 的业务关联 ID。
- 物品配置 ID、技能 ID 等不能随意修改的业务标识。

系统根据确定的关系图进行逐级映射。不能在所有数据中搜索某个数字并直接替换。

对于无法自动判断的业务关联，通过项目配置指定复制、映射、保留或断开策略。

## 7. 本地导入

支持两种模式：

**全新测试数据库：** 在确认没有主键冲突时，可以选择保留原始 DBID。

**现有测试数据库：** 新建 DBID，逐级插入子表并修复关联关系。

执行过程：

1. 校验归档完整性。
2. 检查目标引擎与数据库 Schema。
3. 检查主键、唯一键及账号冲突。
4. 生成导入计划。
5. 在本地事务中执行写入。
6. 获得新 ID 并更新关联。
7. 验证记录和引用关系。
8. 提交事务。
9. 可选使用 KBEngine 原生加载接口验证 Entity。

不自动迁移不兼容 Schema，也不对正在运行的本地 Entity 直接覆盖数据库状态。

## 8. 安全要求

- 源数据库账号最小权限，只允许 SELECT。
- 目标连接必须明确标记为本地或测试环境。
- 导入操作必须经过 Dry Run。
- 生产账号凭据、令牌、支付信息默认不复制。
- 数据归档支持加密与完整性校验。
- 操作日志避免包含原始玩家隐私。
- 提供超时、最大记录数、最大数据量限制。
- 失败时回滚事务；提交后清理操作必须单独确认。

## 9. 开发阶段

| 阶段 | 核心交付 |
|---|---|
| Phase 0 | 核实 Kode、KBEngine 的真实数据库映射与测试样本 |
| Phase 1 | Schema Resolver、关系图、Export Planner |
| Phase 2 | 只读导出和归档 |
| Phase 3 | Import Planner、IDMap、冲突预览 |
| Phase 4 | 本地事务导入与原生 Entity 加载验证 |
| Phase 5 | VSCode 一键导出与一键导入界面 |
| Phase 6 | 性能、安全、兼容性和回归测试 |

## 10. MVP 验收标准

第一版必须通过一个真实 KBEngine 测试工程验证：

- 可以导出一个持久化 Avatar。
- 可以完整导出 Avatar 对应的 ARRAY、组件等引擎生成子表。
- 可以导入到本地 MySQL。
- 新数据库 ID 与子表关系全部正确。
- 导入失败不会产生部分角色数据。
- 导入后的角色可以被 KBEngine 通过原生数据库加载流程读取。
- 源数据库不发生任何写入。
- 对不支持的业务关联和不一致的 Schema 给出明确错误。

**完成上述闭环后，才进入复杂业务引用和更高级的数据迁移功能开发。**

## 11. 后续版本

**v0.2：** 复杂嵌套子表、自定义业务引用、本地账号绑定、多次复制同一角色、完整可视化预览。

**v0.3：** 不同 KBEngine 分支适配、扩展数据源、归档版本兼容与高级数据脱敏。

最终产品应专注于 KBEngine 持久化玩家数据的跨环境调试复制，而不是逐步演变成另一套游戏运营后台。


## 最重要的三个技术难点

| 难点 | 我在计划书中的处理方式 |
|--------|--------|
| **嵌套子表的 ID** | 建立有类型的关系图，不能假设所有 `parentID` 都直接指向 Avatar 的 DBID |
| **业务自定义关联** | 引擎关系自动处理，Account/Avatar、Guild 等业务引用通过显式规则配置 |
| **数据一致性** | 在支持条件下使用 MySQL InnoDB 只读一致性事务，但明确不能把数据库快照当成最新内存状态 |

KBEngine 的实际数据库布局包含 Entity 主表、组件及自定义类型生成的表，而 MySQL 的一致性快照也有明确的存储引擎和事务隔离条件。

## 开发顺序建议

我最建议让 Code Agent **先完成 Phase 0，不要直接开始写 ExportExecutor**。

因为现在最影响正确性的不是 SQL 查询，而是确认 KBEngine 真正的 `parentID` 关联方式、嵌套 ARRAY 的主键规则以及 Account/Avatar 的引用结构。

这些事实确认后，导出和导入的实现反而比较直接。
