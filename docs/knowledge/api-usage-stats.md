## What the scan measures

1. **`KBEngine.<name>`** — every attribute access on the `KBEngine` module
   object (functions and constants alike).
2. **Entity API members** — `X.<member>` accesses where `<member>` exists in
   the C-21 API-docs library (`crates/kode-server/assets/api-docs.json`, 225
   entries). Note the top rows: `id`/`position` are built-in entity
   properties whose counts include ordinary client-side field reads — the
   number measures *presence in code*, not API "call" intensity.
3. **Callbacks defined** — `def onXxx(...)` declarations, classified into
   engine-known groups (names verified against the knowledge pages:
   entity lifecycle, client/proxy lifecycle, timer/trigger, db/archive,
   global/space data, entry-script SPI) versus **project-defined** handlers
   (the engine never calls them; project code does).

## Patterns worth copying (observed combinations)

- **Timer discipline**: `addTimer` at 8 occurrences vs `onTimer` at 10
  definitions — trees consistently implement `onTimer(timerID, userArg)` and
  dispatch on the timer identity (`if userArg != TIMER_THINK: return`,
  `templates/demo-game/scripts/cell/Monster.py:139-145`). Notably `delTimer`
  is **never called** (0 occurrences)
  even though 8 timers are added: consistent with the lifecycle article
  (timers are cancelled wholesale on destroy — the `destroy()` macro calls
  `scriptTimers_.cancelAll()`, `entity_macro.h:1021` at `kbengine@3082ab5`),
  so explicit cancellation only matters for cancelling early while the entity
  lives. A repeating timer that should stop on a condition *before* destroy
  must call `delTimer` — the demo trees never demonstrate this pattern.
- **Cell creation pair**: `createCellEntity`/`createCellEntityInNewSpace`
  chosen per "entity already has a space?" — always followed by an
  `onGetCell` implementation (4/4 in these trees).
- **Remote-handle direction**: `cell` (24) ≫ `base` (6) — business logic
  drives the cell from the base; `client` (18) broadcast sits between.
- **Interfaces face**: the polling pair
  `registerReadFileDescriptor`/`deregisterReadFileDescriptor` always appears
  together (4/4), matching the Poller pattern in the interfaces demo.
