## Def & Entity Intelligence

- **kbengine-def language & grammar** — `.def` files get a dedicated language id, bracket rules and a TextMate grammar — (evidence: package.json#contributes.languages, package.json#contributes.grammars)
- **Real-time .def diagnostics** — unknown types / Flags / DetailLevel values, duplicate property & method definitions, missing Type/Flags fields, with a master switch — (evidence: package.json#configuration `kbengine.diagnostics.*`, `kbengine.enableDiagnostics`; src/defAnalyzer.ts)
- **Structured .def validation** — duplicate definitions, tag placement and missing-field checks behind `kbengine.enableStructureDiagnostics` — (evidence: package.json#configuration `kbengine.enableStructureDiagnostics`; src/defAnalyzer.ts)
- **Quick Fix: unknown type correction candidates** — the unregistered-type diagnostic (stable code `kbengine.unknownType`) offers QuickFix replacements drawn from registered types only (builtins + types.xml + entities), case-normalized edit distance ≤ 2, distance-sorted and capped at 5; edits touch only the current document, no declarations are auto-created — (evidence: src/languageProviders.ts `KBEngineTypeCodeActionProvider`, `UNKNOWN_TYPE_DIAGNOSTIC_CODE`)
- **Code Action: generate empty implementation for unimplemented def methods** — acting on a def method declaration whose owner script exists but lacks the method, offers a single Refactor action whose title shows the target file and insertion line; the skeleton is `def name(self, arg0..argN)` with `pass` body, `<Arg>` count driving the parameter list; the insertion point is computed from the target file's current text (open buffer preferred); already-implemented methods (same query face as Go to Implementations) are not offered again — (evidence: src/languageProviders.ts `KBEngineMethodImplementationCodeActionProvider`; src/entityMapping.ts `listOwnerScriptFilesForIdentity`)
- **Python receiver-None diagnostics** — `self.cell`/`self.base`/`self.client` member use without a null guard (positive `if`, early exit, alias, `hasattr`) flags a Warning citing the engine getter source; calling a `.def` method via a receiver whose section does not declare it flags a section mismatch — (evidence: package.json#configuration `kbengine.receiverNoneDiagnostics`; src/receiverNoneDiagnostics.ts)
- **Receiver-aware def section gating** — property Flags resolved into base/cell/client visibility domains that gate sections and ordering — (evidence: src/defAnalyzer.ts `propertyFlagDomainList`; commit c69517e)
- **Hover: tag / value / symbol docs** — .def tag explanations, type-Flags-DetailLevel value docs and custom property/method summaries — (evidence: package.json#configuration `kbengine.hover.showTagDocs|showValueDocs|showSymbolDocs`; src/languageProviders.ts)
- **Hover: types.xml storage shape** — where a custom type lands in the database (builtin column, FIXED_DICT flatten, ARRAY child table recursion) — (evidence: todo.md:20; package.json#configuration `kbengine.hover.typeStorage`; src/languageProviders.ts `describeTypeStorageShape`)
- **Hover: Implemented-By reverse link** — def method hover shows the script implementation location — (evidence: package.json#configuration `kbengine.hover.implementedBy`; todo.md:111)
- **Hover: entity registration** — entities.xml registration info (Utype number, list position, total count) — (evidence: package.json#configuration `kbengine.hover.entityRegistration`)
- **Hover: merged def chain** — Parent chain + interfaces + component slots as one inheritance-closure hover — (evidence: package.json#configuration `kbengine.hover.defChain`; todo.md:31; src/defChain.ts)
- **Hover: event stats** — registration/listening counts for event constants (event callback reverse links) — (evidence: package.json#configuration `kbengine.hover.eventStats`; src/eventApi.ts)
- **Hover: server config values** — kbengine.xml server config entries with value and explanation — (evidence: package.json#configuration `kbengine.hover.serverConfig`; src/serverConfigHover.ts)
- **Hover: persistent property DB location** — persistent properties show full `db`.`tbl`.`col` name plus engine DDL fragment and limits — (evidence: todo.md:69, todo.md:124; src/databaseSchema.ts `describePropertyDatabaseStorage`)
- **Hover: def-method / receiver-call / builtin-property annotations (Python)** — hovering a `def`-declared method name in a Python implementation script shows the def-declared method annotation under the same parameter-count / annotation-type gate as the RPC lens; `self.<section>.<method>` calls resolve per-section def candidates, and a section mismatch gives no annotation; single-segment `self.<property>` access shows the builtin-property facet annotation; each async branch is bounded by the hover total budget instead of spinning, with the timed-out layer logged — (evidence: package.json#configuration `kbengine.entity.receiverSections`, `kbengine.entity.builtinProperties`, `kbengine.hover.asyncBudgetMs`; src/languageProviders.ts `provideHover` def-method / receiver-call / builtin-property branches; src/hoverBudget.ts `raceWithBudget`)
- **CodeLens: RPC methods** — def-declared Exposed methods marked at their Python implementation lines — (evidence: package.json#configuration `kbengine.codeLens.rpc`; todo.md:74; src/rpcCodeLens.ts)
- **CodeLens: event callbacks** — event callback/subscription markers in Python scripts — (evidence: package.json#configuration `kbengine.codeLens.eventCallbacks`; todo.md:27; src/eventApi.ts)
- **CodeLens: property access reverse jump** — `self.<property>` access lines link back to the def declaration with type/visibility/persistent info — (evidence: package.json#configuration `kbengine.codeLens.property`; todo.md:21; src/propertyCodeLens.ts)
- **CodeLens: types.xml storage lens** — per-type "lands in table X" lens chain with reference back-scan, folded beyond 10 usages — (evidence: package.json#configuration `kbengine.codeLens.typesXml`; todo.md:20; src/languageProviders.ts `TypesXmlCodeLensProvider`)
- **Inlay hints: def-declared data types** — `self.<property>` access sites show the types.xml data type inline; `self.base/cell/client` RPC call sites show the declared parameter types (`argN: type`) after each argument — (evidence: package.json#configuration `kbengine.inlayHints.typeData`; todo.md:25; src/typeInlayHints.ts)
- **Inlay hints: def parameter types at definition sites** — entity script sections (`ClientMethods`/`BaseMethods`/`CellMethods`) render the `.def`-declared `<Arg>` type after each un-annotated `def` parameter, plus `-> type` when `<ReturnType>` is declared — (evidence: package.json#configuration `kbengine.inlayHints.defParams`; src/defParamInlayHints.ts)
- **entities.xml validation** — duplicate entity names get a warning (engine silently merges) plus a Utype list-order hover — (evidence: todo.md:33; src/entitiesXmlAnalysis.ts)
- **Cross-file inheritance checks** — same-name checks across the inheritance chain; Interfaces loading semantics aligned to the engine — (evidence: todo.md:65, todo.md:66; src/defAnalyzer.ts `collectInheritedNames`)
- **Python navigation (F12 / rename / call hierarchy)** — owner-aware navigation with C3-MRO and mixin composition-root resolution, `kbengine.python.enableMroJump` toggle — (evidence: package.json#configuration `kbengine.python.enableMroJump`; src/languageProviders.ts, src/pythonClassIndex.ts, src/entityMapping.ts)
- **Cold-completion refreshable state (`self.` member completions)** — when the mapping index has not finished its initial scan, `self.<prefix>` completions return an empty `CompletionList` marked `isIncomplete: true` (the editor re-queries as typing continues) instead of a final null; no permanent miss is recorded, so the same prefix yields def-declared members once the index lands; after the scan completes, python files without a def mapping still return null (a true miss is not reported refreshable) — (evidence: src/entityMapping.ts `isInitialScanComplete`; src/languageProviders.ts `PythonCompletionProvider` cold branch)
- **Call chain (Show Call Chain)** — expands the outgoing calls of a def/Python entity method through the def index: depth 3 by default, following `self.base/cell/client.<method>()` receiver calls to other def-declared methods, unresolved targets drawn as open-ended nodes; rendered as a bundled offline mermaid graph (default `graph`, CSP-free, no CDN) or a plain text fallback, with the in-panel tab choice persisted to workspace state and taking precedence over the setting, and a graph render failure falling back to text with a header notice — (evidence: package.json#contributes.commands `kbengine.python.showCallChain`; package.json#configuration `kbengine.python.callChainHints|callChainView`; src/defCallChain.ts `buildDefCallChain`/`renderDefCallChainMermaid`, src/defCallChainProvider.ts, src/defCallChainViewLogic.ts)
- **Database schema view** — entity/component/ARRAY child-table schemas rendered read-only from def analysis, with property→table jump and F12 support — (evidence: package.json#contributes.commands `kbengine.database.open`; todo.md:124, todo.md:133; src/databaseSchema.ts)
- **SQL templates** — per-table full SELECT, property-column SELECT and child-table JOIN statements, honoring a configurable table prefix — (evidence: todo.md:126; package.json#configuration `kbengine.db.tablePrefix`; src/databaseSchema.ts `renderTableSqlLines`)
- **MySQL drift check (read-only)** — compares code-side schema against the real database; missing/extra/type-mismatched columns reported, SELECT-only whitelist plus session read-only — (evidence: package.json#contributes.commands `kbengine.database.checkDrift|checkAllDrift`; todo.md:125; src/databaseDrift.ts)

## Project Model

- **Project profile identity store** — each KBEngine assets/engine combination is saved as its own profile with a persistent stable ID (assigned once at creation, stored per workspace in `workspaceState` and read back after restart); the display name is only a mutable field — renaming a profile or having two same-named profiles never merges or loses identity; roots are saved per profile (`saveRoots` touches only the target record's path fields, so re-saving one profile's assets/engine roots never bleeds into another and both read back independently after restart) — (evidence: src/projectProfiles.ts `ProjectProfileStore`)
- **Existing project import** — pick the assets root and the four faces (entities/defs/scripts/engine) are identified via the shared convention chain, with any face not found previewed honestly as 未识别 (not identified); the preview lists all four results and only picking 导入 creates the profile — Esc or dismissing any step writes nothing, and a folder with no KBEngine structure at all is rejected without a preview — (evidence: package.json#contributes.commands `kbengine.project.import`; src/projectImport.ts `identifyProjectLayout`/`importExistingProject`)
- **Interpreter source per profile** — each profile records which Python interpreter it uses and where it came from (the `kbengine.python.interpreterPath` setting if the file exists, else python3/python located on PATH, else an explicit missing state — never a fabricated path); the import confirmation shows the interpreter state inline, and records saved before this field existed read back as missing rather than being dropped — (evidence: src/profileInterpreter.ts `resolveInterpreterWith`/`describeInterpreterState`; src/projectProfiles.ts `saveInterpreter`)
- **Python language service status check** — reports 未安装/未启用/已激活 for `ms-python.vscode-pylance` from registration + activation + install-directory evidence; an extraPaths write is never counted as availability, only called out with an explicit caveat — (evidence: package.json#contributes.commands `kbengine.python.serviceStatus`; src/pythonLanguageServiceStatus.ts `classifyPythonService`)
