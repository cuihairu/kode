- **Per-profile database connection selection (DB-001)** — connection configs and query-result caches are both keyed by profileId: switching projects reads the new profile's own config and never reuses another profile's connection (an unselected profile returns a plain null, no neighbor fallback; a failed config resolve records that profile as config-less); the result cache stores the same SQL per profile separately, TTL expiry and clearProfile touch only the target profile; configs persist through an injected load/save (workspaceState-shaped) and reopen per-profile, while the cache is session-level — never written to disk, so stale rows never impersonate fresh queries — (evidence: src/databaseConnectionRegistry.ts)
- **Single-table read-only preview (DB-002)** — the preview statement is a fixed `SELECT * FROM \`table\` LIMIT N` shape, re-checked through the existing databaseDrift assertReadOnlyStatement before execution (double guarantee); the default row limit is 100 and an explicit limit may not exceed the hard cap of 1000; if the runner ignores LIMIT and returns more rows, the result face slices to the limit and marks truncated; table names accept identifier characters only — a backtick, whitespace, or semicolon is rejected outright, never spliced into the statement — (evidence: src/databaseTablePreview.ts, src/databaseDrift.ts)
- **Query cancel and timeout lifecycle (DB-003)** — a slow query returns timeout/cancelled immediately (no dead waiting), but connection release waits for the underlying promise to settle and then calls close exactly once — the slow query ends, waits, and releases; the polling loop exits as soon as settle/cancel/timeout hits, leaving no background poller behind; an underlying failure surfaces honestly as a failed outcome carrying the original error while the release path still runs; a close failure is visible through the released promise without disturbing the already-decided terminal state; clock, sleep, and cancel probe are all injected — a fast query settles within one macrotask boundary with zero naps — (evidence: src/databaseQueryLifecycle.ts)
- **Result-column source links (DB-004)** — each query-result column links back through the virtual-schema field descriptor: a derived column carries its def declaration site (filePath + line, the click-to-navigate face) plus the declared type verbatim; a descriptor flagged synthetic (engine structural columns like id/sm_autoLoad) is labeled a synthetic column with no def declaration site; a column absent from the schema is honestly unknown — never guessed synthetic, never borrowed from a neighbor table (table matching is the caller's snapshot.tableIndex job, this module only reads the table it is given) — (evidence: src/databaseColumnSource.ts, src/databaseSchema.ts)
- **Entity schema-change impact preview (DB-005)** — diffing two generations of the entity's virtual schema lists added/removed/type-changed columns; a pure computation module with zero injection surface and zero IO — no path exists to execute DDL or write to the database (the preview is a list; applying anything is not this module's face); type comparison uses the derived mysql type (typeLabel), so equivalent source-text changes (aliases) produce no entry; engine synthetic columns stay out of the impact face (a def change does not touch engine structural columns) — (evidence: src/databaseSchemaImpact.ts, src/databaseSchema.ts)
- **Database simulation & export** — simulated table structures exportable as JSON/Markdown — (evidence: package.json#contributes.commands `kbengine.database.simulate|exportSimulation`; todo.md:71; src/databaseSimulator.ts)

- **Automatic hot reload** — file watchers trigger a named quick action with debounce, off by default — (evidence: package.json#configuration `kbengine.hotReload.*`; todo.md:52; src/hotReload.ts)
- **Hot-reload status bar (HR-UI-001)** — a status bar item tracks the watch state machine Off → Ready → Sending → Sent(unverified) → Failed with throttled rendering; a completed action without errors is only "sent, unverified" (no business-receipt check, never claims applied); clicking the item opens the 「KBEngine 热更」 audit log (time / trigger files / debounce / outcome per trigger) — (evidence: package.json#contributes.commands `kbengine.hotReload.showLog`; src/hotReloadStatus.ts, src/hotReload.ts)
- **Per-target hot-reload state isolation (HOT-001)** — the hot-reload delivery ledger isolates results by file's scan root (rootId) × server instance (targetId): the same file sent to different instances gets its own record each, a later target's outcome neither overwrites nor reuses the previous target's green state, and querying another target never sees its neighbour's records; a resend to the same target/file overwrites with the latest — this is the foundation the receipt states (sent_unverified/accepted/applied from HOT-002 on) tighten on, with wiring landing alongside the receipt pipeline — (evidence: src/hotReloadTargetState.ts)
- **HTTP hot-reload delivery recorded as unverified (HOT-002)** — delivery classification trusts transport facts only: 2xx = delivered, recorded as sent-unverified (green but explicitly not confirmed at the application layer); non-2xx or transport failure = failed, naming the status code or cause; the response body is never treated as application evidence (a body claiming applied/ok does not upgrade the verdict — receipt interpretation is HOT-003+); verdicts land directly on the HOT-001 per-target ledger — (evidence: src/hotReloadDelivery.ts, src/hotReloadTargetState.ts)
- **Single-target accepted receipt parsing (HOT-003)** — the recorded protocol: JSON `{"status":"accepted","file":"<echoing the sent file verbatim>"}` (an optional `"targetId"` must match the target when present; extra fields are ignored — only recorded fields count); only a field-by-field match upgrades that (rootId,targetId,file) record to accepted — the file echo pins the receipt to the file it accepts; unknown structures (non-JSON / non-object / status other than accepted) and other status values (applied is HOT-004's verification surface; ok/queued unrecorded) keep the record unverified — no guessing, no upgrading — (evidence: src/hotReloadReceipt.ts, src/hotReloadTargetState.ts)
- **Single-target applied verification (HOT-004)** — the applied-receipt protocol: JSON `{"status":"applied","file":"<verbatim echo>","digest":"<sha256 hex of the sent content>"}`; the digest is recomputed from the sent content with the stock primitive (node:crypto sha256) and only a match marks applied (trusted digest + verified receipt, two proofs); a missing/mismatched digest or a non-conforming receipt keeps the record as-is — no upgrading; the timeout settle keeps still-unconfirmed records unconfirmed (unconfirmed-timeout), never faking a failure or an applied; revision evidence-label semantics are HOT-008's surface — this level trusts the digest only — (evidence: src/hotReloadAppliedCheck.ts, src/hotReloadTargetState.ts)
- **Structural def-change marking (HOT-005)** — a structure fingerprint with two faces: the serialization face (per-property `{Type,Flags}` read from the property's child elements plus the property-name set) and the RPC face (per-method Arg type signatures across the three method sections BaseMethods/CellMethods/ClientMethods plus the method-name set); any fingerprint difference (property add/remove/Type/Flags change, method add/remove/signature change) is structural → marked restart-required and never auto-sent as a plain Python reload; comments/whitespace/reordering/description text/default values stay out of the fingerprint = non-structural, eligible for the plain reload path; a parse failure on either side is conservatively structural (can't prove no structural change → don't auto-send); the def auto-apply master switch wires up later with the receipt pipeline — this module only classifies — (evidence: src/hotReloadDefStructure.ts, src/defParser.ts)
- **Per-target batch aggregation with partial outcome (HOT-006)** — cross-target rollup over the delivery ledger: per-target outcome is the worst file record under it (any failed → failed, else any sent-unverified → sent-unverified, else any accepted → accepted, all applied → applied — a green file never covers a red file on the same target); batch status: every target failed → all-failed, some failed some not → partial, none failed → all-succeeded, no records → no-targets; each target's reason is a per-file `file → outcome(detail)` listing so two targets with one success and one failure show partial with both causes inspectable; success means the delivery surface — sent-unverified never masquerades as applied — (evidence: src/hotReloadBatchSummary.ts, src/hotReloadTargetState.ts)
- **Retry failed targets only (HOT-007)** — retry walks the batch rollup (HOT-006) targets and re-sends only to targets whose outcome is failed; the confirmed-success side (applied/accepted/sent-unverified — already delivered) is never re-sent, since a re-send would be a duplicate delivery; cancellation is probed before each hop and stops all subsequent sends — completed actions are kept, never-initiated ones are marked skipped-cancelled (not faked as sent); the send function is injected and this module never touches the ledger — re-sent results land through the existing HOT-002..004 surfaces — (evidence: src/hotReloadRetry.ts, src/hotReloadBatchSummary.ts)
- **Revision evidence source labels (HOT-008)** — three evidence kinds each carry a source label: fileHash (locally recomputed file-content hash), semanticHash (structural fingerprint), engineDigest (reported by the runtime receipt) — never one blanket term; formatting lists label + truncated value + origin per line; comparison is same-kind only: cross-kind is always incomparable, so a coincidentally equal fileHash and engineDigest never counts as agreement (a local hash never impersonates runtime evidence); the evidence report lists only the kinds actually provided — no placeholder lines for missing kinds — (evidence: src/hotReloadRevisionEvidence.ts)
- **Live-validation input register (LIV-001)** — the required inputs for real-engine live validation in three sections: target version (kbengine repo URL + ref), component addresses (component names taken from the existing COMPONENT_NAMES vocabulary — machine's broadcast port, cellappmgr for the space-list query, cellapp/baseapp for watcher path queries), and startup conditions (demo server up with components discovered, a login-capable demo account); the default register is all-unregistered + no instance, and the status text says plainly 缺实例/未测 (no instance → untested) — never claiming validation that did not run; registration is a pure-function merge that leaves the original register untouched; lastVerifiedAt is the post-validation write-back slot — (evidence: src/liveValidationInputs.ts, src/kbengineProtocol.ts)

## Project Model

- **Project profile identity store** — each KBEngine assets/engine combination is saved as its own profile with a persistent stable ID (assigned once at creation, stored per workspace in `workspaceState` and read back after restart); the display name is only a mutable field — renaming a profile or having two same-named profiles never merges or loses identity; roots are saved per profile (`saveRoots` touches only the target record's path fields, so re-saving one profile's assets/engine roots never bleeds into another and both read back independently after restart) — (evidence: src/projectProfiles.ts `ProjectProfileStore`)
- **Active profile selection** — the active profile is remembered by its stable ID (workspaceState), so renaming never loses the selection; each real switch (new ID ≠ old ID) fires exactly one change event other features can subscribe to, re-picking the same profile fires nothing; an unknown ID is refused and a selection whose record was removed resolves honestly to null — (evidence: package.json#contributes.commands `kbengine.project.selectActive`; src/activeProfile.ts `setActiveProfile`/`onDidChangeActiveProfile`)
- **Profile health summary** — the active profile's health is summarized with four issue kinds (根歧义 assets root gone, 缺引擎 engine root unrecorded/gone, 缺解释器 interpreter unrecorded/gone, 缺语言服务 the PRJ-005 check reporting anything other than active), each carrying its own navigation entry (re-import command / interpreter setting / service-status command); all healthy is a single message, issues open a picker where a picked row jumps to its entry — (evidence: package.json#contributes.commands `kbengine.profile.health`; src/profileHealth.ts `collectProfileHealth`/`showProfileHealthSummary`)
- **Language index follows profile switches** — the active profile's assets root becomes the index input (ahead of the `kbengine.assetsRoot` setting and auto-discovery; a selected root that no longer exists falls through honestly to the normal chain); a switch removes the old external roots from the indexes (the SNP-009 removal path) and advances the root-config generation, so in-flight scan batches started under the old profile write nothing into the current snapshot — the new input is rebuilt by the next scan — (evidence: src/scanRoots.ts `setActiveProfileScanRoot`; src/entityMapping.ts `performScanEntityMappings` generation gate; extension.ts `onDidChangeActiveProfile` wiring)
- **Launch follows the active profile** — the next launch resolves the engine bin from the active profile's engineRoot (`kbe/bin/server` under it) and the config root from its assetsRoot (ahead of the `kbengine.binPath`/`kbengine.assetsRoot` settings and auto-discovery, per field: an empty field falls through honestly to the settings chain; a profile config root is authoritative — no silent fallback to workspace discovery); resolution happens at launch time by stable ID (no cache, so a switch needs no re-wiring), and each registered instance snapshots the bin/config roots and profile ID it actually started with — switching profiles afterwards never touches a running instance's record, pid, or process; a same-key start while registered is still refused (already-running), and the selected profile only takes effect from the next launch — (evidence: src/serverManager.ts `getActiveProfileLaunchRoots`; src/serverManager.ts `RunningServer.binPath`/`configPath`/`profileId`)
- **Existing project import** — pick the assets root and the four faces (entities/defs/scripts/engine) are identified via the shared convention chain, with any face not found previewed honestly as 未识别 (not identified); the preview lists all four results and only picking 导入 creates the profile — Esc or dismissing any step writes nothing, and a folder with no KBEngine structure at all is rejected without a preview — (evidence: package.json#contributes.commands `kbengine.project.import`; src/projectImport.ts `identifyProjectLayout`/`importExistingProject`)
- **Interpreter source per profile** — each profile records which Python interpreter it uses and where it came from (the `kbengine.python.interpreterPath` setting if the file exists, else python3/python located on PATH, else an explicit missing state — never a fabricated path); the import confirmation shows the interpreter state inline, and records saved before this field existed read back as missing rather than being dropped — (evidence: src/profileInterpreter.ts `resolveInterpreterWith`/`describeInterpreterState`; src/projectProfiles.ts `saveInterpreter`)
- **Python language service status check** — reports 未安装/未启用/已激活 for `ms-python.vscode-pylance` from registration + activation + install-directory evidence; an extraPaths write is never counted as availability, only called out with an explicit caveat — (evidence: package.json#contributes.commands `kbengine.python.serviceStatus`; src/pythonLanguageServiceStatus.ts `classifyPythonService`)
- **Minimal project creation template** — a fixed manifest lists every directory and file a new empty KBEngine project needs (relative paths, file contents included, scripts layout aligned with the shared discovery conventions so the skeleton is importable); creation planning probes each target path up front — any existing target is reported as a conflict with its exact path, and the preview lists one row per entry with its exact absolute path — (evidence: src/projectTemplate.ts `MINIMAL_PROJECT_TEMPLATE`/`planProjectCreation`/`buildProjectCreationPreviewItems`); the create command wires the manifest to disk with the full generator protection set — refuse-on-conflict before any preview, the shared generator confirm QuickPick, atomic file writes, and roll-back-everything-this-run on failure, then registers the profile through the same identification chain as the import command — (evidence: package.json#contributes.commands `kbengine.project.create`; src/projectCreate.ts `createMinimalProject`)
