## 0. 结论速览

| 面 | 结论 | 一句话依据 |
| --- | --- | --- |
| P0-1a（索引维护） | **不值得** | TS 修法已把维护降到线性并锁死；两面同为 O(自身类)，Rust 只有常数因子，无数量级空间 |
| P0-3c（大文件解析，.def/types.xml） | **值得**（R2 放行） | 内存 9.3×–33.8× 是真数量级；def 解析 6.7×–11.9×、巨型文件 14.6×；worker 隔离只救了 Python 面的响应性，没救成本与内存 |
| 交互热路径（hover/def/completion） | **不值得** | P0 后热路径全部亚毫秒；瓶颈已不在计算层 |
| 全量 Python 冷扫 | **不值得**（为提速迁移） | 107.7s → 4.88s（22×，TS 修法拿满）；剩余 ~5s 属后台扫描，非交互延迟 |
| 增量指纹 | **不需要 Rust** | TS 换指纹实现即可解决（BigInt FNV-1a → 32 位分块）；这条是「不必迁移也能修」的反例 |

**总判断：有边界的值得。** 迁移的唯一数据支撑面是 `.def`/`types.xml` 解析+实体索引的**内存与大文件超线性**（正是 R2 原型范围）；其余面上 TS 修法已把算法复杂度与交互延迟问题清掉，Rust 拿不到数量级收益。R3（tower-lsp 骨架）继续等 R2 对拍过闸。

## 2. TS 残余成本 top3（按当前数据）

### ① 内存峰值（parser 层）——最大的真实差距

head2head 实测（§3.4）：TS 峰值 70.8 / 229.6 / **1,154 MiB**（T1/T2/T3），Rust 2.9 / 6.8 / 124.1 MiB，**9.3×–33.8×**；T3 上 TS 峰值 = 输入字节的 **117×**，Rust 12×。V8 对短命 AST 的堆保留（含 `src/defParser.ts:69` 全文文本键 8 份文档缓存的强引用风险，head2head §5.1 已记录）在用户机器上就是真实 RSS。30k 资产集的卡顿体感与这条最吻合——CPU 热路径是亚毫秒的，内存压力不是。**P0 系列修复没有触碰内存轮廓**（快照/线性化或有小改善，未单独量测）。

### ② 大文件解析超线性（.def/XML 面）

TS 单属性成本随文件增大涨 4.1×（14.8 → 60.4 µs/属性），Rust 基本线性（3.3 → 4.1）；20,000 属性 MEGA.def 单文件 TS 1,127–1,288 ms vs Rust 82.6 ms（**14.6×**）；全量吞吐 6.7×–11.9×。P0-3c 的 worker 隔离覆盖的是 **Python** 大文件（响应性：宿主不再被阻塞），`.def` 解析仍在扩展宿主内同步进行，成本与内存原样。注意 R2 范围（.def+types.xml）恰好就是这个未隔离面。

### ③ 增量零重建的指纹成本——不需要 Rust 的反例

TS 二扫零重建 1.08 s/10 MB，其中 **99% 是 `contentFingerprint`（BigInt 逐字节 FNV-1a）**；Rust 同式指纹 16.6 ms（64×）。但 head2head §4.3 的结论同样成立：**TS 侧换指纹实现（32 位双通道/分块）即可消除**，与迁移无关。且无论是否迁移，TS 对照腿都要先修这条，否则对拍数据没有意义。

## 3. 两面直接回答

### 3.1 P0-1a 面：Rust 能否比 TS 修法拿数量级收益？——不能

- TS 修法后维护是 O(该文件自身类数)（`unindexFile` 只迭代 fileCache 旧记录），且 `tests/pythonIndexMaintenance.test.ts:19` 用操作计数（`bucketReads===2,000`）把线性锁死。
- Rust 实现同一语义同样只能做 O(自身类) 删除——算法下界相同，差距只剩 Map 操作的常数因子。数量级收益不存在。
- 该面修复前后的实际收益（22× 冷扫提速）已由 TS 修法兑现完毕。**为维护面迁移：不值得。**

### 3.2 P0-3c 面：Rust 能否比 TS 修法拿数量级收益？——内存能，解析接近一个数量级

- TS 修法（worker_threads 隔离）解决的是**响应性**（宿主不卡），不改变解析成本与内存峰值——1.4 MB 巨型 def 仍要 1 秒级、117× 输入字节的堆。
- Rust 已实测：内存 **9.3×–33.8×**（真数量级）；def 解析吞吐 6.7×–11.9×、巨型文件 14.6×（超线性尾巴被消掉）；线性扩展（每属性成本恒定）。
- 但边界要说清：这些数字全部来自 **.def/entities/types/alias XML 面**。**Python 大文件**（big-py 8,000 方法）没有 Rust 解析器，R2 范围也不含 Python；Python 面的 TS worker 隔离已是当前最优解，迁移论证不覆盖它。
- **为 .def/types.xml 解析+实体索引面迁移：值得，数据支撑 R2 放行。**

## 4. 取舍记录

1. **R2 放行**（.def+types.xml quick-xml 带位置解析器 + 实体索引，与 TS 同语料对拍）：本审计的数据支撑面。验收口径沿用 head2head 的金丝雀思路（SURFACE 语义面同值 + 位置感知 diff + 增量零重建断言）。
2. **不迁移清单**：索引维护（§3.1）、调度器/等待链（P0-2 已锁）、交互 provider 层（热路径亚毫秒）、UI/命令/Webview（提案原文同判）。
3. **无论迁移与否都先做**：TS `contentFingerprint` 换实现（§2.③）——对照腿自身的增量数据才有意义；以及 `defParser.ts:69` 全文键缓存的强引用上限复查（head2head §5.1 风险，属内存面）。
4. **R3 继续双闸**：R1（本审计）+ R2（对拍一致）都过才启动 tower-lsp 骨架。
5. **观察项**：S4 big-py 编辑后 P99 尖峰（79.9 → 147 ms，单轮 n=20，量级未变）与 def-heavy 首扫漂移（652 → 1,010 ms）——同量级不判回归，但纳入下次复测对照；交互端到端 P95 的真值仍以 P0-4c 现场验收为准，本审计不做「热路径已达标」的泛化结论（P0-4d 红线）。

## 5. 未覆盖（如实标注）

- 本轮未量测扩展宿主进程级 RSS（P0-4b 现场项）；内存结论引自 parser 层纯进程口径。
- 单轮运行，无置信区间；跨机器绝对值禁止比较（PERF-015）。
- Rust 侧数字不含跨进程 IPC/序列化成本（若走常驻 LSP）；head2head 两侧均为纯进程口径。
- Python 解析的 Rust 对照不存在，Python 面的「不值得」是范围判断而非数据结论。
