# Rust 迁移收益复审（2026-11-08）

用户问题：若性能处于同一数量级，是否还有必要迁移？

结论：停止以全面迁移为目标；保留有收益证据的解析核心，对其余模块按实际交互收益、资源预算和维护成本逐项决定。没有证据的模块暂缓新增迁移，不因此删除已经运行的实现。数量级不是唯一门槛：同为百毫秒，900ms→100ms 也可能值得；同为毫秒，3ms→1ms 通常不足以独立支撑跨语言重构。

## 证据范围

本次读取现有基准报告、原始输出、基准驱动与当前调用链；未重新运行性能基准。以下数字均为历史记录，不代表当前 HEAD 的复测结果。不同日期、语料、构建模式和调用边界的数据不用于直接计算整体收益比例。

输入已找到：

- [解析器基准与方法](../perf/2026-parser-head2head.md)、[原始输出](../perf/2026-parser-head2head-run.txt)：2026-10-23，TS 纯 Node 进程、Rust release，同语料，无 IPC。
- [R1 审计](2026-10-27-r1-migration-data-audit.md)：含 TS 算法修复后的扫描记录与后续纠偏。
- [服务态报告](../perf/2026-11-08-serving-state.md)、`tests/perf/servingState.bench.ts`：真实 client/server RPC，合成语料，驱动使用 debug 二进制。
- [Schema 取舍](2026-10-29-dbschema-migration-tradeoff.md)、[消息表取舍](2026-10-29-messagetable-migration-tradeoff.md)：早期基线，不能当作当前实现状态。
- 当前 `src/languageProviders/{navigation,completion,hover,validation}.ts`：用于核对接线，静态证据不代替性能测量。

缺失：当前同机同项目、同功能语义的 TS 后台化与 Rust release 端到端 A/B；扩展宿主与后台进程总内存对照；完整正确性、取消与未保存缓冲区等价性验收。

## 已有数据实际支持什么

| 范围 | 历史记录 | 可支持的判断 |
|---|---|---|
| DEF/XML 全量解析，28 文件 | TS 5.317ms，Rust 0.448ms | 倍数明显，但绝对节约约 5ms，单次低频使用价值有限 |
| DEF/XML 全量解析，1352 文件 | TS 118.720ms，Rust 10.803ms | 批量解析有潜在价值；实际冷启动还受 I/O、镜像、索引成本影响 |
| DEF/XML 全量解析，2001 文件约 10MB | TS 3529.788ms，Rust 525.584ms | 大语料有秒级计算节约，值得保留并复测 |
| 合成 20000 属性巨型 DEF | TS 约 1.1–1.3s，Rust约 83ms | 极端大文件有显著收益，不能代表典型文件 |
| 独立解析进程峰值内存，约 10MB 语料 | TS 1154.2MiB，Rust 124.1MiB | 支持该解析实现的内存优势，不等于整个插件节省九倍内存 |
| Python 冷扫描，TS 修复前后 | 107737ms→4880ms | 算法和调度修复无需改语言也能有大幅收益；不是 TS/Rust A/B |
| Rust 服务态查询 | definition P50 1.71ms，completion 0.72ms，diagnostic 2.93ms | 证明所测 RPC 响应时间；不证明完整 provider 比 TS 更快 |

解析基准中 `SURFACE` 属性/方法计数一致是基础校验，不足以单独证明全部语义和位置等价。增量二扫的 46–88 倍差距主要来自 harness 中 TS BigInt 指纹实现，不应作为必须迁移到 Rust 的理由。峰值内存包括不同运行时、缓存与重复解析的影响，不是语言本身不可改变的固定差距。

## 当前收益论证的三处缺口

1. **查询延迟没有可比 A/B。** 服务态报告把 3000 个合成 DEF 的 Rust RPC 与另一基线的 TS 热态查询并列，调用边界和语料不一致，且服务端为 debug、机器负载较高。不能据此证明相对性能不受影响、没有回归或没有必要回退。需要实际 provider 返回时间与事件循环延迟。
2. **整体内存没有可比 A/B。** 服务态报告记录后台进程约 8.8→118.6MB；另一个 TS 扫描记录是不同语料下的 RSS 增量/峰值。既不能由此证明两者等价，也不能搬用独立解析器 9–34 倍优势证明服务态内存优势。TS 索引仍保留时，双份语料和缓存可能抵消收益；总量应包含扩展宿主与所有新增子进程，并统一稳态/峰值口径。
3. **定义跳转仍重复执行。** 当前 `navigation.ts::provideDefinitionRustFirst` 先执行并等待 `provideDefinitionImpl`，再请求 Rust。因此 Rust 成功也没有省下 TS 计算成本。`validation.ts` 同样先产生 TS 诊断，再异步请求 Rust。这些路径不能按“已替换 TS 计算”计收益。completion/hover 的 Rust-first 形态不同，需分别评估。

## 分模块建议

| 模块 | 建议 | 理由与复评条件 |
|---|---|---|
| DEF/XML 解析与共享语义索引 | 保留候选核心，优先复测 | 唯一已有明确解析耗时与内存优势的范围；避免把完整 AST 反复跨进程传回 |
| Hover/Completion/Definition 的 VS Code 装配 | 保留 TS，后台按需查询 | 装配迁移本身无计算收益；热点查询复用后台索引，失败再执行 TS，避免正常路径双算 |
| Python 解析、类索引、MRO | 暂缓扩大迁移 | 没有当前等价 Rust/TS 后台化对照；先核对同步派生计算、失效与缓存，再测 |
| 扫描、调度与缓存维护 | 优先优化现有架构 | 历史 TS 修复已有大幅收益；后台化可用 TS worker/进程，不是 Rust 独有 |
| Schema、消息表、SDK 生成、配置推导 | 不以性能为由继续扩面 | 历史记录多为低频/已缓存任务，当前批量需求若改变则重测；既有 Rust 实现可因共享模型保留，但不能冒称已提速 |
| 协议解析、Wireshark 导出 | 区分负载再决定 | 生成 Lua/导出文件不要求 Rust；持续高吞吐解码若有实测资源差距才构成性能理由；独立 CLI/原生插件复用另计 |
| 玩家克隆与归档 | 按正确性和复用决定 | 加密、序列化、数据库操作 TS 也可做，不能用新增能力存在证明语言迁移收益 |
| UI、命令、配置与编辑器 API | 保留 TS | 没有已确认的性能迁移理由 |

已有独立 Rust CLI、MCP、原生插件可能有共享实现的维护收益；这是产品和复用理由，与“修复扩展卡顿”分别核算。全部反向重写也有成本，本结论不要求推倒现有 Rust。

## 后续是否迁移的判据

先固定真实项目、操作、功能语义、缓存状态与资源预算，再比较现有 TS、合理后台化/优化后的 TS、Rust release。TS 不必为了对照被无限优化，但不能拿已知坏算法作迁移依据。

测量冷启动/首次可用、热态和未命中 P50/P95/P99、编辑更新、事件循环延迟、峰值及稳态总内存、CPU、取消与结果正确性。按同机交替多轮记录机器负载；服务缺失回退单列，不能混进 Rust 成功样本。

当双方均满足目标且差异对用户无感时，默认选择维护成本更低的方案，不新增迁移。即使查询同为毫秒级，若 Rust 显著降低内存、宿主阻塞或大项目冷启动，也可能值得；必须由该指标的可比测量支持。当前已接受的 [ADR-002](../kode2/adr/ADR-002-benchmark-first-rust-migration.md) 本就要求逐模块基准驱动，而非整体重写。
