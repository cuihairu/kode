## 3. 判定

**暂缓,不推进 Rust Python 解析原型。** 理由:

1. **交互面不痛**:hover/注解查询实付 1–9ms(真机),解析不落在请求路径上(HOV-010 快照级联)。
2. **编辑面主线程已被结构卸载**:超阈值(256KiB)文件解析派发 worker 线程,主线程实付 commit 段 4–10ms;次阈值常见体量文件解析 p50 0.7–21ms,单次编辑一次性成本,处于或低于可感知门槛。
3. **解析不是用户可感知主要成本**:三档语料中 parse 占编辑面 CPU 的大头(S 87%、M 98%、L 98%),但用户感知通道(主线程阻塞、请求延迟)都已被 worker 派发与快照级联截住——「CPU 占比高」不等于「用户可感知瓶颈」。
4. **Rust 侧无从复用**:R2 索引无任何 Python 语义(r2-index-inventory §4【缺失】),原型是净新建解析器而非迁移;def/XML 侧 6.7×–11.9× 优势(head2head)属已完成的 R1,不构成 Python 侧证据。
5. **无反向数据**:修复后没有出现归因到解析的用可感知卡顿样本(S4 尾值不可归因、样本不足)。

## 4. 复评触发(任一成立即重开)

1. **真机遥测证伪**:languageServiceMetrics 聚合(现 14 类事件)在真实使用中出现次阈值文件的 document-parse p95 持续 >50ms(主线程可感知)。
2. **worker 通道失效场景**:worker 不可用回退同步解析(阈值检查失效/线程崩溃回退)成为常态路径,超阈值文件重新阻塞主线程。
3. **编辑负载画像变化**:用户真实项目常态编辑超阈值文件且 commit 段(p50 4.2ms)随语义增量化之外的索引增长越出预算(如 >30ms)。
